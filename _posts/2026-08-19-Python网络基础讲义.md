# Python 网络基础讲义：从一次 LLM 请求读懂 HTTP、HTTPS、TCP、DNS、反向代理、长连接与流式传输

这是一份面向大模型开发新手的网络讲义。目标不是背协议名，而是让你能顺着一次真实请求定位问题：用户为什么连不上服务、为什么 HTTPS 报错、为什么模型流式输出被“攒”到最后、为什么 Nginx 返回 502，以及为什么重试会造成重复扣费。

本文围绕一条典型链路学习：浏览器或 Python 客户端请求 `https://api.example.com/v1/chat`，DNS 找到入口 IP，TCP 与 HTTPS 建立可靠加密通道，反向代理把请求转发给 Python 服务，Python 再调用模型服务并把 token 流式返回。文中的地址、域名和令牌均为示例，不能直接用于生产环境。

## 1. 学完后应该能做什么

完成本文后，你应能：

- 画出 DNS、TCP、TLS、HTTP、反向代理和 Python 应用在一次请求中的先后关系。
- 区分 IP、端口、域名、URL、HTTP 方法、请求头、请求体、状态码与响应体。
- 理解 HTTPS 是 HTTP 运行在 TLS 加密通道上，而不是另一套业务协议。
- 用 Python 发起 HTTP 请求、解析 URL、查询 DNS、建立最小 TCP 回显服务。
- 判断“连接复用”“长连接”“流式 HTTP”“SSE”“WebSocket”分别解决什么问题。
- 配置并理解最小 Nginx 反向代理，知道哪些超时和缓冲配置会影响 LLM 流式输出。
- 用可观察的证据排障，而不是看到任何网络错误都盲目重试。

本文不讲内核级拥塞控制算法、BGP 路由协议或完整 TLS 密码学证明。它们很重要，但不应阻塞你先把服务请求链路跑通。

## 2. 先建立全景图：一次请求到底经过了什么

假设网页向 LLM 服务发送问题：

```text
浏览器 / Python 客户端
  -> DNS：api.example.com 对应哪个 IP？
  -> TCP：与 IP:443 建立可靠字节流连接
  -> TLS：验证证书并协商加密参数
  -> HTTP：POST /v1/chat，发送 JSON 请求体
  -> Nginx：终止 TLS、转发、负载均衡、记录访问日志
  -> FastAPI：鉴权、校验、调用上游模型
  -> 上游模型：逐个产生 token
  -> FastAPI / Nginx：按块或 SSE 事件回传
  -> 客户端：边收到边渲染
```

这里的顺序非常关键：HTTP 不能在尚未建立的 TCP 连接上凭空传输；HTTPS 先完成 TLS，再传 HTTP；反向代理通常先收到公网请求，再把它转给内网 Python 进程。

可以把它类比为寄件：DNS 是查地址簿，IP 是楼栋地址，端口是具体房间号，TCP 是可靠运输合同，TLS 是防拆封的加密包装，HTTP 是信封内规定好的业务表单，Python 程序才是实际处理业务的人。

## 3. 网络分层：不要把不同层的问题混为一谈

工程中最实用的简化模型如下：

| 层次 | 你关心的对象 | 典型问题 | 常见工具 |
| --- | --- | --- | --- |
| 名称与寻址 | 域名、IP、端口 | 域名解析不到、连错环境 | `nslookup`、`socket.getaddrinfo` |
| 传输 | TCP/UDP 连接、字节流 | 连接拒绝、超时、断开 | `Test-NetConnection`、`ss`、日志 |
| 安全 | TLS 证书、SNI、加密 | 证书过期、主机名不匹配 | `openssl s_client`、客户端异常 |
| 应用 | HTTP 方法、头、体、状态码 | 401、404、429、500、JSON 错误 | `curl`、浏览器开发者工具、`httpx` |
| 网关与服务 | Nginx、Python、模型服务 | 502、504、缓冲、并发耗尽 | Nginx/access/error 日志、应用指标 |

排障时先问“失败在哪一层”。例如：

- DNS 解析失败时，请求还没有抵达 TCP，更不可能是 FastAPI 路由写错。
- TCP 连接成功但 TLS 校验失败时，防火墙和端口大概率没问题，重点是证书、域名或系统时间。
- HTTP 返回 `401` 说明网络与服务至少已经通了，应该查令牌、鉴权配置或权限，而不是改 DNS。
- `502 Bad Gateway` 通常表示 Nginx 能工作但拿不到有效上游响应；`504 Gateway Timeout` 通常表示上游超过了代理等待时间。它们不能直接证明 Python 代码有 bug。

## 4. 地址、端口、域名和 URL

### 4.1 IP 与端口

IP 用于把数据送到一台主机或网络接口；端口用于把同一台主机上的数据交给对应服务。`203.0.113.10:443` 中，`203.0.113.10` 是 IP，`443` 是 HTTPS 的常用端口。

一条 TCP 连接由下面四元组唯一标识：

```text
客户端 IP : 客户端临时端口 <-> 服务端 IP : 服务端端口
```

所以许多客户端能同时连接同一个 `IP:443`，因为每个客户端的 IP 或临时端口不同。服务进程会在固定端口“监听”，操作系统把新连接交给它。

### 4.2 域名与 URL

域名是便于人记忆且可变更映射的名字，例如 `api.example.com`。URL 是完整资源定位符：

```text
https://api.example.com:443/v1/chat?stream=true
\___/   \_____________/ \_/ \_______/ \__________/
协议          主机名      端口   路径       查询参数
```

- `https`：协议方案；默认端口为 443。
- `api.example.com`：主机名，后续会通过 DNS 解析为 IP。
- `:443`：显式端口；若省略则按协议默认端口。
- `/v1/chat`：路径，通常由应用路由匹配。
- `stream=true`：查询参数，适合筛选或简单开关；不要放密钥，因为 URL 容易出现在日志、历史和代理记录中。

Python 可用标准库安全地拆解 URL，避免自己用字符串切分：

```python
"""演示使用标准库解析 URL 的组成部分。"""
from urllib.parse import parse_qs, urlparse


def inspect_url(url: str) -> None:
    """打印 URL 中与网络请求相关的字段。

    Args:
        url: 需要解析的完整 URL。
    """
    parsed = urlparse(url)
    print("协议:", parsed.scheme)
    print("主机:", parsed.hostname)
    print("端口:", parsed.port)
    print("路径:", parsed.path)
    print("查询参数:", parse_qs(parsed.query))


inspect_url("https://api.example.com:443/v1/chat?stream=true&model=demo")
```

## 5. DNS：域名怎样变成 IP

DNS（Domain Name System）是分布式的名称解析系统。客户端通常会先问本机缓存、操作系统配置的递归 DNS 服务器，再由递归服务器按需要查询权威 DNS 服务器。你不必手写这一链路，但必须知道 DNS 结果会被缓存，改完解析记录不一定立刻在所有地方生效。

常见记录：

| 记录 | 含义 | 例子 |
| --- | --- | --- |
| `A` | 域名到 IPv4 地址 | `api.example.com -> 203.0.113.10` |
| `AAAA` | 域名到 IPv6 地址 | `api.example.com -> 2001:db8::10` |
| `CNAME` | 别名到另一个域名 | `api -> gateway.example.net` |
| `MX` | 邮件服务器 | 邮件路由 |
| `TXT` | 文本验证或策略 | 域名验证、SPF |

TTL（生存时间）告诉缓存多久可以复用一条记录。较短 TTL 有助于快速切换，但会增加 DNS 查询量；较长 TTL 降低查询量，但事故切流更慢。发布前先确认旧记录会被缓存多久。

在 Windows PowerShell 中查询：

```powershell
Resolve-DnsName api.example.com
nslookup api.example.com
```

Python 中使用 `socket.getaddrinfo`。它会让系统完成实际解析，并可能同时返回 IPv4 和 IPv6：

```python
"""演示查询一个主机可用的地址与端口信息。"""
import socket


def resolve_host(host: str, port: int = 443) -> None:
    """查询域名的候选连接地址。

    Args:
        host: 要解析的域名。
        port: 目标服务端口。
    """
    addresses = socket.getaddrinfo(host, port, type=socket.SOCK_STREAM)
    for family, socktype, protocol, _, sockaddr in addresses:
        family_name = "IPv6" if family == socket.AF_INET6 else "IPv4"
        print(f"{family_name}: {sockaddr}, 协议编号: {protocol}")


resolve_host("example.com")
```

注意：DNS 成功只说明“得到了候选地址”，不代表目标端口开放、TLS 正确或 HTTP 路由存在。反过来，浏览器能访问一个网站也不证明你的 Python 运行环境使用的是相同 DNS、代理或 IPv6 路径。

### DNS 常见故障

- `socket.gaierror` 或“找不到主机”：域名拼错、DNS 服务不可用、内网域名只能在 VPN 内解析，或容器 DNS 配置异常。
- 本机与服务器解析到不同 IP：检查 DNS 分流、缓存、hosts 文件、不同区域的负载均衡和 IPv4/IPv6 差异。
- 刚改解析仍访问旧服务：检查 TTL、CDN/浏览器缓存和发布平台的 DNS 生效状态。
- 用 IP 访问 HTTPS 成功不了：TLS 证书通常签发给域名，主机名校验和 SNI 也依赖域名。

## 6. TCP：可靠字节流，不是“消息队列”

TCP 提供面向连接、可靠、有序的字节流。它负责处理丢包重传、乱序重排、重复数据、流量控制与拥塞控制。应用读到的是连续字节，不会自动保留你 `send()` 时的“消息边界”。

### 6.1 三次握手与四次挥手

建立连接的简化过程：

```text
客户端                           服务端
SYN  ------------------------->  收到连接请求
     <-------------------------  SYN + ACK
ACK  ------------------------->  连接建立，可传输应用数据
```

关闭连接常见为双方分别发送结束信号，因此常被称为四次挥手。你不需要手动发送这些报文，但要理解关闭是正常生命周期的一部分，不是所有 `Connection reset` 都等于程序崩溃。

### 6.2 TCP 不保证“每次 recv 得到一条完整消息”

这是新手最容易踩的坑。下面的错误代码假设一次 `recv` 必然读完一条 JSON：

```python
# 错误示例：TCP 只保证字节流，不能假设一次 recv 就得到完整 JSON。
data = connection.recv(4096)
```

真实环境中，数据可能被拆成多次到达，也可能多条逻辑消息合在一次到达。解决办法是由应用协议定义边界，例如固定长度头、分隔符或长度前缀。HTTP 已经定义了头部与请求体边界，所以一般不要自己在 HTTP 之下再发明 JSON 分帧协议。

下面是只用于理解 TCP 的最小长度前缀回显服务。生产服务请使用成熟 HTTP/ASGI 服务器而不是自行实现协议：

```python
"""演示 TCP 长度前缀协议，帮助理解字节流与消息边界的区别。"""
import socket


def recv_exactly(connection: socket.socket, size: int) -> bytes:
    """从 TCP 连接持续读取，直到得到指定数量的字节。

    Args:
        connection: 已建立的 TCP 连接。
        size: 期望读取的字节数。

    Returns:
        恰好读取到的字节。

    Raises:
        ConnectionError: 对端在消息读取完成前关闭连接时抛出。
    """
    chunks: list[bytes] = []
    remaining = size
    while remaining:
        chunk = connection.recv(remaining)
        if not chunk:
            raise ConnectionError("对端在消息未完成时关闭连接")
        chunks.append(chunk)
        remaining -= len(chunk)
    return b"".join(chunks)


def serve_once(host: str = "127.0.0.1", port: int = 9000) -> None:
    """监听一次连接，读取长度前缀消息后原样回显。

    Args:
        host: 仅本机练习使用的监听地址。
        port: 练习端口。
    """
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server:
        server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        server.bind((host, port))
        server.listen()
        connection, address = server.accept()
        with connection:
            print("客户端已连接:", address)
            length = int.from_bytes(recv_exactly(connection, 4), "big")
            payload = recv_exactly(connection, length)
            connection.sendall(len(payload).to_bytes(4, "big") + payload)


if __name__ == "__main__":
    serve_once()
```

配套客户端：

```python
"""向 TCP 练习服务发送一条长度前缀消息并读取回显。"""
import socket


def send_message(message: str) -> None:
    """发送 UTF-8 文本并验证回显。

    Args:
        message: 要发送的文本。
    """
    payload = message.encode("utf-8")
    with socket.create_connection(("127.0.0.1", 9000), timeout=3) as client:
        client.sendall(len(payload).to_bytes(4, "big") + payload)
        response_length = int.from_bytes(client.recv(4), "big")
        response = client.recv(response_length)
        print(response.decode("utf-8"))


send_message("你好，TCP")
```

上例客户端为简化演示，对长度字段和短消息各调用一次 `recv`；严谨生产协议中客户端也应复用 `recv_exactly`，因为任何一次 `recv` 都可能读不全。

### 6.3 超时、连接拒绝与重置

- `Connection refused`：目标 IP 可达，但端口没有监听服务，或防火墙主动拒绝。检查服务是否启动、端口是否正确、容器端口是否映射。
- `ConnectTimeout`：在规定时间内没有建立连接。可能是网络不通、丢包、防火墙静默丢弃、目标过载，不能简单断言是代码问题。
- `ReadTimeout`：连接已建立，但等待响应数据超时。常见于上游慢、死锁、代理读超时或模型长时间不产生首 token。
- `Connection reset by peer`：对端或中间设备突然中断连接。检查服务重启、进程崩溃、负载均衡空闲超时和客户端取消。

## 7. HTTP：在 TCP 之上约定业务请求与响应

HTTP 是应用层协议。HTTP/1.1 文本格式便于观察，一次请求大致如下：

```http
POST /v1/chat HTTP/1.1
Host: api.example.com
Authorization: Bearer <短期访问令牌>
Content-Type: application/json
Accept: application/json

{"model":"demo","messages":[{"role":"user","content":"你好"}]}
```

响应：

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-Request-ID: req_123

{"id":"chat_1","output":"你好，有什么可以帮助你？"}
```

### 7.1 方法、状态码与幂等性

| 方法 | 常见意图 | 通常是否幂等 |
| --- | --- | --- |
| `GET` | 查询资源 | 是 |
| `POST` | 创建资源、触发生成 | 通常否 |
| `PUT` | 用完整表示替换资源 | 是 |
| `PATCH` | 局部更新资源 | 不一定 |
| `DELETE` | 删除资源 | 语义上通常是 |

幂等表示“用相同输入执行多次，最终可观察状态与执行一次相同”。它不代表响应内容完全相同，也不代表没有副作用日志。网络出现超时时，是否重试取决于操作是否可安全重复：`GET` 常可有限重试，创建订单、扣费、提交任务或启动模型生成的 `POST` 则应配合幂等键，不能盲目重发。

常见状态码：

| 状态码 | 含义 | 首先检查什么 |
| --- | --- | --- |
| `200` | 成功 | 响应内容是否符合契约 |
| `201` | 创建成功 | 新资源 ID、Location 或响应体 |
| `400`/`422` | 请求格式或字段非法 | 客户端参数与 JSON 结构 |
| `401` | 未认证或凭据无效 | Authorization、令牌过期、时钟 |
| `403` | 已认证但无权限 | 角色、租户、对象级授权 |
| `404` | 路径或资源不存在 | URL、版本、路由和资源 ID |
| `409` | 状态冲突 | 幂等键、并发更新、当前状态 |
| `429` | 被限流 | 退避、配额、并发数、响应头 |
| `500` | 服务内部异常 | 服务端日志、请求 ID |
| `502` | 代理没得到有效上游响应 | Nginx 上游地址、进程、协议 |
| `503` | 服务暂不可用 | 健康检查、容量、发布状态 |
| `504` | 网关等待上游超时 | 上游耗时和代理超时 |

### 7.2 请求头不是“可选装饰”

请求头承载协议元数据。最常见的有：

- `Host`：目标主机；反向代理用它区分多个站点。
- `Authorization`：身份凭据。日志中必须脱敏，不能打印完整令牌。
- `Content-Type`：请求体格式，例如 `application/json`。
- `Accept`：客户端期望的响应格式；SSE 使用 `text/event-stream`。
- `User-Agent`：客户端标识，适合诊断但不应作为安全认证。
- `X-Request-ID`：请求追踪 ID，用于把代理、应用和上游日志串起来。
- `Cache-Control`：缓存指令；包含私密结果时必须审慎。

### 7.3 HTTP 版本与连接复用

HTTP/1.1 默认支持持久连接（常被口语称为 Keep-Alive）：一次 TCP/TLS 连接可承载多个按顺序的 HTTP 请求，避免每次都握手。它不等于“永不关闭的连接”，连接仍可能因空闲超时、服务发布、代理策略或网络变化而关闭。

HTTP/2 在一个 TCP 连接内多路复用多个请求流，减少 HTTP/1.1 队头阻塞；HTTP/3 基于 QUIC/UDP，进一步改善某些网络环境下的传输问题。作为应用开发者，优先确保 HTTP 语义、超时、取消和代理配置正确，不要因为“用了 HTTP/2”就假设所有性能问题都会消失。

## 8. HTTPS：HTTP + TLS，保护传输中的机密性与身份

HTTPS 并不是“加密后的 URL”，而是 HTTP 在 TLS 安全通道中传输。TLS 主要提供：

- 机密性：中间人不能直接读到请求体、令牌和响应内容。
- 完整性：内容被篡改可被检测。
- 身份认证：客户端根据证书确认正在连接预期域名的服务。

简化握手：

```text
客户端 -> 服务端：支持的 TLS 版本、密码套件、随机数、SNI 主机名
服务端 -> 客户端：选定参数、证书、随机数
客户端：验证证书链、有效期、域名和信任根
双方：协商会话密钥，之后加密传输 HTTP 数据
```

证书验证不能为了“先跑通”而关掉。`verify=False` 只可在隔离的临时诊断中使用，且绝不能进入生产代码；它会让中间人攻击变得可行。

TLS 常见问题：

- `CERTIFICATE_VERIFY_FAILED`：证书过期、自签名证书未被信任、缺少中间证书、系统 CA 过旧，或证书的域名不匹配。
- 访问 `https://IP地址` 失败：证书通常只包含域名，主机名校验会失败。
- 只有某台机器失败：检查系统时间、系统根证书、企业代理证书和运行环境差异。
- Nginx 配置了证书但仍打不开：检查 443 监听、防火墙、安全组、域名解析、`server_name` 与证书匹配关系。

使用 `curl` 查看响应头与握手结果：

```powershell
curl.exe -v https://example.com/
```

不要把包含真实 `Authorization` 的完整 `curl -v` 输出发到公开聊天、issue 或日志系统。

## 9. 用 Python 正确地调用 HTTP 服务

Python 标准库可以完成基础请求；在现代服务开发中，常见选择是 `httpx`，它同时支持同步、异步、连接池、超时配置与流式读取。

安装练习依赖：

```powershell
python -m pip install httpx
```

### 9.1 同步 JSON 请求：明确超时与错误边界

```python
"""演示向 HTTP API 发送 JSON 请求，并区分网络与 HTTP 错误。"""
import os

import httpx


def ask_model(question: str) -> dict[str, object]:
    """调用示例模型接口并返回已验证为 JSON 对象的响应。

    Args:
        question: 用户问题。

    Returns:
        服务返回的 JSON 对象。

    Raises:
        RuntimeError: 缺少访问令牌或响应体不是 JSON 对象时抛出。
        httpx.HTTPError: 网络、超时或非成功 HTTP 状态时抛出。
    """
    api_key = os.environ.get("DEMO_API_KEY")
    if not api_key:
        raise RuntimeError("请先在环境变量中配置 DEMO_API_KEY")

    timeout = httpx.Timeout(connect=5.0, read=60.0, write=10.0, pool=5.0)
    headers = {"Authorization": f"Bearer {api_key}"}
    payload = {"model": "demo", "messages": [{"role": "user", "content": question}]}

    with httpx.Client(timeout=timeout) as client:
        response = client.post("https://api.example.com/v1/chat", headers=headers, json=payload)
        response.raise_for_status()
        data = response.json()

    if not isinstance(data, dict):
        raise RuntimeError("服务响应不是预期的 JSON 对象")
    return data
```

超时应拆开理解：

- `connect`：建立 TCP（以及通常随后的 TLS）连接最多等多久。
- `read`：两次接收响应数据之间最多等多久；流式响应不应把它误设为很短的总请求时长。
- `write`：上传请求体最多等多久。
- `pool`：等待连接池可用连接最多等多久。

`response.raise_for_status()` 会把 4xx/5xx 转为异常。它不能替代检查业务字段，例如 HTTP `200` 的 JSON 内仍可能有模型拒答、异步任务失败或部分结果标记。

### 9.2 连接池：复用客户端，而不是每个请求都新建

在服务进程中，应把 `httpx.Client` 或 `httpx.AsyncClient` 作为应用生命周期资源复用。每个请求都创建客户端会频繁建立连接、浪费 TLS 握手，还可能耗尽临时端口。下面展示一个简化的异步调用：

```python
"""演示在应用生命周期内复用异步 HTTP 客户端。"""
import httpx

client = httpx.AsyncClient(timeout=httpx.Timeout(60.0, connect=5.0))


async def fetch_health(url: str) -> dict[str, object]:
    """请求健康检查接口。

    Args:
        url: 健康检查 URL。

    Returns:
        解析后的 JSON 对象。
    """
    response = await client.get(url)
    response.raise_for_status()
    return response.json()


async def shutdown_client() -> None:
    """在应用优雅关闭时释放连接池中的网络资源。"""
    await client.aclose()
```

真实 FastAPI 项目可用 lifespan 管理器创建和关闭客户端。不要在 `async def` 中直接调用长时间阻塞的 `requests` 或同步 SDK；这会阻塞事件循环，影响同一进程的其他请求。

## 10. 反向代理：为什么公网通常不直接暴露 Uvicorn

反向代理位于客户端与应用服务器之间。客户端认为自己访问的是 `api.example.com`，但代理会把请求转发给内网地址，例如 `127.0.0.1:8000`。Nginx、Caddy、Traefik 都可承担这类角色。

它常负责：

- TLS 证书与 HTTPS 终止，避免每个 Python 服务都管理证书。
- 域名与路径路由，例如 `/api/` 转给 API，`/` 返回前端静态文件。
- 负载均衡，把流量分给多个应用实例。
- 请求体大小限制、访问日志、基础限流、压缩与安全响应头。
- 与上游服务隔离：Python 只监听内网或回环地址，减少暴露面。

最小 Nginx 配置示例：

```nginx
server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    client_max_body_size 10m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 120s;
        proxy_send_timeout 120s;
    }
}
```

应用若要生成绝对回调 URL、执行安全跳转或记录真实协议，需要正确理解 `X-Forwarded-Proto` 等转发头；但不能无条件信任来自公网客户端伪造的转发头。应只信任由自己控制的代理写入的头，并按框架文档配置受信任代理。

### 10.1 502、503、504 的定位顺序

当用户看到代理错误页，建议依次检查：

1. 在代理机器本地请求上游：`curl http://127.0.0.1:8000/health`。
2. 检查应用进程是否存活、监听地址和端口是否与 `proxy_pass` 一致。
3. 检查 Nginx 错误日志中的上游连接信息。
4. 若本地上游正常，再检查代理超时、负载均衡目标、容器网络和发布时连接排空。
5. 用请求 ID 对照 Nginx access log、应用日志和模型上游日志。

不要把 `502` 直接翻译成“前端问题”或“模型坏了”。它是网关与上游之间的边界信号，需要证据继续定位。

## 11. 长连接：至少要区分四个概念

“长连接”在交流中常被混用，建议每次明确指哪一种：

| 概念 | 连接是否持续 | 通信方向 | 适合场景 |
| --- | --- | --- | --- |
| HTTP 持久连接 | 可复用多个请求，但会空闲关闭 | 请求-响应 | 常规 API |
| 长时间 HTTP 响应 | 一个请求很久才结束 | 服务端响应 | 大文件、长任务等待 |
| SSE | HTTP 响应持续推送事件 | 服务端 -> 客户端 | LLM token、进度、通知 |
| WebSocket | 握手后维持双向连接 | 双向 | 聊天协作、实时控制 |

长连接不是免费资源。每条连接占用文件描述符、内存、连接池槽位，可能占用应用 worker 或上游模型并发名额。生产系统必须有连接数上限、空闲超时、心跳、取消路径、慢客户端处理和监控。

### 11.1 心跳与空闲超时

客户端、代理、负载均衡器和 NAT 设备都可能在空闲一段时间后断开连接。心跳是周期性的小数据，用于确认连接活着并防止空闲回收。它不是用来掩盖服务卡死的手段：连续心跳正常而业务迟迟无首 token，仍应通过业务超时、追踪和告警定位上游。

SSE 常使用注释形式的心跳：

```text
: heartbeat

```

WebSocket 可使用协议 ping/pong 或应用层 `{"type":"ping"}`/`{"type":"pong"}`。消息必须定义版本、类型、请求 ID 与错误语义，不能只靠“收到一段字符串”猜业务状态。

## 12. 流式传输：从字节块到可用的 LLM 体验

流式传输的核心是服务器不等到完整结果才返回，而是在结果产生时连续写入响应。它主要改善 TTFT（首 token 时间）和主观交互体验；它不必然降低总生成时间。

### 12.1 HTTP 分块与缓冲

HTTP/1.1 可以使用 `Transfer-Encoding: chunked` 把未知总长度的响应分段发送。框架通常会代你处理分块细节，但端到端是否真正“边生成边到达”还取决于：

- 上游模型 SDK 是否真在逐块产生数据。
- Python 生成器是否持续 `yield`，并在等待时让出事件循环。
- 应用服务器是否缓冲。
- Nginx/CDN 是否缓冲或压缩。
- 浏览器、前端解析器或命令行客户端是否缓冲。

所以必须进行端到端验证：用 `curl -N` 或浏览器界面观察首段到达时间，不能只看服务端日志中调用了 `yield`。

### 12.2 FastAPI 的最小流式文本接口

```python
"""演示将异步生成器作为 HTTP 流式响应返回。"""
import asyncio
from collections.abc import AsyncIterator

from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()


async def generate_chunks(prompt: str) -> AsyncIterator[str]:
    """模拟逐块生成文本。

    Args:
        prompt: 用户输入，仅用于组成演示内容。

    Yields:
        可立即发送给客户端的 UTF-8 文本片段。
    """
    for text in ["正在回答：", prompt, "。", "这是", "流式", "结果。"]:
        await asyncio.sleep(0.3)
        yield text


@app.get("/generate")
async def generate(prompt: str) -> StreamingResponse:
    """返回逐段抵达的纯文本响应。

    Args:
        prompt: 用户问题。

    Returns:
        使用分块 HTTP 响应传输的文本流。
    """
    return StreamingResponse(
        generate_chunks(prompt),
        media_type="text/plain; charset=utf-8",
        headers={"Cache-Control": "no-cache"},
    )
```

启动后验证：

```powershell
uvicorn main:app --reload
curl.exe -N "http://127.0.0.1:8000/generate?prompt=什么是流式传输"
```

### 12.3 SSE：把流定义为有边界的事件

对于 LLM 前端，SSE（Server-Sent Events）通常比“裸文本分块”更好，因为事件有名字、数据和结束边界。每个事件以空行结束：

```text
event: token
data: {"text":"你"}

event: done
data: {"usage":{"output_tokens":1}}

```

服务端示例：

```python
"""演示将生成内容封装为 SSE 事件。"""
import asyncio
import json
from collections.abc import AsyncIterator

from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()


async def sse_events(prompt: str) -> AsyncIterator[str]:
    """产生 token、错误或完成事件。

    Args:
        prompt: 用户输入。

    Yields:
        符合 SSE 格式的事件文本。
    """
    try:
        for token in ["你", "好", "，", "这是", "流式", "回答"]:
            await asyncio.sleep(0.2)
            payload = json.dumps({"text": token}, ensure_ascii=False)
            yield f"event: token\ndata: {payload}\n\n"
        yield "event: done\ndata: {\"reason\": \"stop\"}\n\n"
    except asyncio.CancelledError:
        # 客户端断开时让取消向上游传播，避免继续消耗模型 token。
        raise
    except Exception:
        # 响应已开始时不能再改 HTTP 状态码，需通过流内错误事件通知客户端。
        yield "event: error\ndata: {\"message\": \"生成失败\"}\n\n"


@app.get("/events")
async def events(prompt: str) -> StreamingResponse:
    """以 SSE 格式返回模型生成事件。

    Args:
        prompt: 用户问题。

    Returns:
        Content-Type 为 text/event-stream 的响应。
    """
    return StreamingResponse(
        sse_events(prompt),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )
```

原生浏览器 `EventSource` 只能发 GET，且不适合携带自定义 Bearer 请求头。若请求需要 JSON 请求体、取消、复杂鉴权或更细的读取控制，前端可用 `fetch` 的流式 `ReadableStream`；无论哪种方式，都不要把长期令牌放到 URL 查询参数。

### 12.4 Nginx 避免把流式内容攒到最后

对仅用于流式路径的 location，可考虑：

```nginx
location /events {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;
}
```

`proxy_buffering off` 不是万能性能开关。它会影响资源使用，应仅用于确实需要低延迟推送的路径，并通过压测与监控验证。若前面还有 CDN、Ingress 或云负载均衡，也要确认其对 SSE/流式响应的缓冲与超时策略。

### 12.5 流式失败、取消与重试

HTTP 响应头发出后，无法把原本的 `200` 改为 `500`。因此流协议应至少定义：

- `meta`：请求 ID、模型、开始时间等。
- `token`：增量文本或结构化增量。
- `error`：稳定错误码与对用户安全的说明。
- `done`：正常完成及用量、结束原因。

用户点击“停止”时，前端应取消读取；服务端应捕获取消，并停止读取上游模型、释放并发信号量与数据库/HTTP 连接。只停止浏览器渲染而让模型继续生成，会浪费 token、容量和费用。

流式结果通常不可安全地透明重试：你无法确定用户已看到了多少内容，也无法保证新一次生成一致。应记录请求 ID、已发送事件数和失败阶段；是否允许“重新生成”应作为用户可见的业务动作，而不是网络层静默重试。

## 13. WebSocket：双向实时通信的边界

WebSocket 以 HTTP 进行升级握手，之后成为全双工消息通道。它适用于客户端和服务端都需要随时发消息的场景，例如协作编辑、实时人工接管、交互式会话控制。

它不天然比 SSE 更高级：若业务只是“用户提交一次问题，服务器连续推 token”，SSE 或 `fetch` 流往往更容易实现、监控和部署。选择协议的依据是通信方向和状态复杂度，而不是“是否实时”。

最小 FastAPI 回显示例：

```python
"""演示 WebSocket 的连接、收发与断开处理。"""
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()


@app.websocket("/ws/echo")
async def echo_socket(websocket: WebSocket) -> None:
    """接收文本并以 JSON 回显。

    Args:
        websocket: 框架提供的双向连接对象。
    """
    await websocket.accept()
    try:
        while True:
            message = await websocket.receive_text()
            await websocket.send_json({"type": "echo", "text": message})
    except WebSocketDisconnect:
        # 正常断连无需按应用错误处理，但可记录连接生命周期指标。
        return
```

生产环境还要补充：握手认证、对象级授权、消息大小限制、速率限制、心跳、断线重连、慢客户端背压、连接数限制和跨实例广播。多 worker 或多机器部署时，内存中的连接列表不能互相看见，需要 Redis Pub/Sub、消息队列或专用实时服务做跨实例分发。

## 14. 面向 LLM 服务的网络可靠性规则

大模型接口比普通 CRUD 更容易遇到慢响应、长连接和高成本重试。以下规则应成为默认检查项：

1. 每一跳都有超时：客户端、Nginx、应用、模型 SDK、数据库和工具调用都要设置合理边界。
2. 超时不等于可重试：连接建立失败、`429`、`503` 等可能短暂；写入、扣费、外部工具执行、已开始流式输出则需要幂等与业务判断。
3. 使用指数退避并加入随机抖动：避免故障时所有客户端同时再次冲击服务。
4. 为可重试的创建型操作使用幂等键：服务端用键关联第一次结果，而不是重复创建任务。
5. 分离并发预算：长时间流式生成会占用连接与模型并发，不能与短健康检查或关键写入共用无限制队列。
6. 记录请求 ID、模型、用户/租户（脱敏后的标识）、状态码、TTFT、总耗时、token 用量和结束原因。
7. 限制输入、输出、连接和请求体大小：这既是稳定性要求，也是安全边界。
8. 不在日志中写入 API Key、完整 Cookie、完整提示词中的敏感内容或原始授权头。

一个简单且可控的重试包装通常只对明确安全的只读请求生效：

```python
"""演示仅对临时网络失败重试的只读请求。"""
import random
import time

import httpx


def fetch_with_retry(url: str, attempts: int = 3) -> httpx.Response:
    """有限次数请求只读 URL，并对网络临时失败使用退避。

    Args:
        url: 要读取的资源 URL。
        attempts: 总尝试次数，必须至少为 1。

    Returns:
        成功的 HTTP 响应。

    Raises:
        ValueError: 尝试次数非法时抛出。
        httpx.HTTPError: 最后一次网络或状态码失败时抛出。
    """
    if attempts < 1:
        raise ValueError("attempts 必须至少为 1")

    with httpx.Client(timeout=httpx.Timeout(10.0, connect=3.0)) as client:
        for attempt in range(attempts):
            try:
                response = client.get(url)
                if response.status_code not in {429, 502, 503, 504}:
                    response.raise_for_status()
                    return response
            except httpx.TransportError:
                if attempt == attempts - 1:
                    raise

            if attempt == attempts - 1:
                response.raise_for_status()
            delay = 0.5 * (2**attempt) + random.uniform(0, 0.2)
            time.sleep(delay)

    raise RuntimeError("逻辑不应到达这里")
```

上例是教学简化，不能直接套给所有接口。`POST /v1/chat` 是否能重试，取决于供应商是否支持幂等、是否已开始扣费或产出流、以及你的产品是否允许重复生成。

## 15. 安全基线

- 生产认证与用户数据必须使用 HTTPS；WebSocket 使用 `wss://`。
- 不要使用 `verify=False` 绕过证书验证；修复证书链、信任根或环境配置。
- API Key 放入环境变量或密钥管理服务，不提交进代码库，不贴到日志和截图中。
- Bearer Token 应短期、最小权限、可撤销；服务端校验过期、签名、受众与权限。
- 反向代理应限制请求体和上传大小，应用仍要重复校验输入。
- 区分 CORS 与认证：CORS 只约束浏览器是否允许脚本读响应，不会阻止其他程序直接调用 API。
- 设置可信代理边界，避免客户端伪造 `X-Forwarded-For`、`X-Forwarded-Proto` 导致审计或安全判断错误。
- 对流和 WebSocket 限制连接数、消息大小、发送速率与空闲时间，防止资源耗尽。

## 16. 从外到内的排障流程

遇到“接口不通”时，按如下顺序收集证据：

1. 确认 URL、环境、方法、请求体和必要的认证头，没有把测试环境当成生产环境。
2. 检查 DNS：域名在当前机器/容器解析成什么地址，是否符合预期。
3. 检查 TCP：目标 `IP:端口` 是否可连接。例如 Windows 可用：

```powershell
Test-NetConnection api.example.com -Port 443
```

4. 检查 TLS：证书、域名、系统时间和企业代理是否正确。用 `curl.exe -v` 仅在安全环境中查看握手线索。
5. 检查 HTTP：状态码、响应头中的请求 ID、错误响应结构是否符合 API 契约。
6. 若经过 Nginx：对比 Nginx access/error 日志与应用日志，确认请求是否抵达应用、何时超时。
7. 若调用模型上游：记录上游请求 ID、TTFT、总耗时、限流信息与取消原因。
8. 最后才修改配置或代码；每次只修一个已定位问题，并重新验证完整链路。

对于流式问题，还需额外测量：服务端首次 `yield` 时间、代理转发首字节时间、客户端首字节时间、事件间隔以及 `done` 是否到达。这样才能分清“模型慢”“代理缓冲”“前端缓冲”和“客户端根本没按流读取”。

## 17. 建议的四周学习与练习路线

### 第一周：地址、DNS、TCP 与 HTTP

- 用 `urlparse` 解析 10 个 URL，说明每一段含义。
- 用 `Resolve-DnsName` 和 `socket.getaddrinfo` 比较域名的 IPv4/IPv6 结果。
- 运行 TCP 回显练习，故意把消息拆成两次发送，观察为何必须处理消息边界。
- 用 `curl.exe -i` 观察一个公开 API 的状态行、头部和响应体。

### 第二周：Python HTTP 客户端与 HTTPS

- 用 `httpx` 实现一个带 `connect`、`read` 超时的 JSON 客户端。
- 人为传入非法请求体，观察 `400`/`422`；传入错误令牌，观察 `401`。
- 观察一个 HTTPS 站点的证书错误信息，理解为何不应关闭验证。
- 在日志中只记录域名、状态码与请求 ID，练习避免输出敏感头。

### 第三周：反向代理与流式传输

- 用 FastAPI 实现健康检查、普通 JSON 响应与 `StreamingResponse`。
- 用 `curl.exe -N` 验证内容是否按块到达。
- 在 Nginx 前面部署该服务，比较开启和关闭代理缓冲的现象。
- 为流协议定义 `meta`、`token`、`error`、`done` 四类事件，并测试中断。

### 第四周：LLM 服务可靠性

- 给模型调用加请求 ID、超时、并发上限与取消传播。
- 区分可重试和不可重试的错误，为安全操作加入带抖动的退避。
- 模拟 Nginx 上游关闭、模型首 token 慢、客户端中途断开三种故障并记录证据。
- 写一页复盘：故障在哪一层、什么证据证明、修复了什么、仍有什么风险。

## 18. 最终自检题

在进入下一阶段前，尝试不查资料回答：

1. URL、域名、IP、端口各自是什么，为什么一个域名可能返回多个 IP？
2. DNS 成功解析为什么不等于 API 可用？
3. TCP 为什么称为字节流，为什么不能假设一次 `recv()` 就读到一条完整消息？
4. HTTPS 比 HTTP 多了哪些保障，为什么不能在生产关闭证书校验？
5. `401`、`403`、`429`、`502`、`504` 分别意味着什么边界问题？
6. HTTP 持久连接、SSE 和 WebSocket 有什么不同？为什么 LLM 单向输出通常不必先用 WebSocket？
7. 服务端已经 `yield` 了，用户仍然最后才看到结果，下一步要检查哪些缓冲层？
8. 为什么对已开始的 LLM 流不能随意自动重试？
9. Nginx 的反向代理在 Python 服务前解决了哪些问题，又引入了哪些需要监控的超时与缓冲？
10. 遇到“请求失败”时，如何从 DNS 到应用日志逐层定位，而不是盲目改代码？

能用“协议层次、请求边界、状态码、超时、日志证据和资源释放”回答这些问题，才算把网络知识真正转化为大模型工程能力。
