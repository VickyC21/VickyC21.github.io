# PyTorch 训练关键参数入门：Batch Size、学习率、梯度裁剪、梯度累积与混合精度

这篇讲义面向刚开始写 PyTorch 训练循环的学习者。目标不是记住几个参数名，而是建立一套能迁移到图像、文本和大模型微调任务中的判断框架：**每次拿多少数据算梯度、每次沿梯度走多远、梯度失控时如何保护、显存不够时如何模拟更大的批量、怎样用较低精度节省显存与提升速度。**

建议按顺序阅读并亲自运行文中的完整示例。开始调参前，请先固定数据集、随机种子、训练轮数、评估指标和日志格式；否则看到的差异可能来自随机性，而不是参数本身。

## 1. 学完后你应能做到什么

- 解释一个 batch、一个 iteration、一个 optimizer step 和一个 epoch 分别是什么。
- 根据显存、吞吐和训练稳定性选择起始 batch size 与学习率。
- 知道学习率过大、过小和 batch size 不合适时，训练曲线通常会出现什么现象。
- 正确地把梯度裁剪放在 `backward()` 之后、参数更新之前；使用 FP16 时先反缩放梯度。
- 使用梯度累积在显存有限时模拟较大的有效批量，并避免忘记除以累积步数。
- 理解 AMP 的 `autocast` 与 `GradScaler` 分别解决什么问题，以及 BF16 和 FP16 的差异。
- 遇到 OOM、loss 为 NaN、梯度不更新或训练不收敛时，有一条可执行的排查顺序。

## 2. 先建立训练循环的地图

一个最小监督学习训练过程可以写成下面的顺序：

~~~text
输入一个小批量数据
  -> 前向传播：模型得到预测值
  -> 计算损失 loss
  -> 反向传播：loss.backward() 计算每个参数的梯度
  -> （可选）处理梯度：反缩放、裁剪
  -> optimizer.step() 根据梯度更新参数
  -> optimizer.zero_grad() 清空本轮梯度
~~~

四个最容易混淆的时间单位如下。

| 名称 | 含义 | 典型代码位置 |
| --- | --- | --- |
| 样本（sample） | 一条训练数据，例如一句文本或一张图片 | Dataset 的一个元素 |
| 小批量（mini-batch） | 一次前向和反向传播处理的一组样本 | DataLoader 每次产出 |
| iteration | 处理一个 mini-batch 的一次循环 | `for inputs, labels in loader` 的一次循环 |
| optimizer step | 真正更新一次模型参数 | `optimizer.step()` |
| epoch | 训练集完整遍历一遍 | 外层循环一次 |

不使用梯度累积时，通常一个 iteration 就对应一个 optimizer step。使用梯度累积后，多个 iteration 才对应一个 optimizer step。这个差别会影响学习率调度器、日志统计和总训练步数。

## 3. 最重要的共同背景：梯度到底是什么

设模型参数为 $\theta$，损失函数为 $L(\theta)$。反向传播会计算梯度 $\nabla_\theta L$，它告诉我们：如果稍微改变每个参数，损失会向哪个方向、以多快的速度变化。

最朴素的梯度下降更新是：

~~~text
θ <- θ - 学习率 × 梯度
~~~

PyTorch 中，下面三行就是核心动作：

~~~python
loss.backward()          # 把当前 batch 的梯度累加到 parameter.grad
optimizer.step()         # 用梯度更新参数
optimizer.zero_grad()    # 清空梯度，为下一轮做准备
~~~

注意 PyTorch 默认**累加**梯度，不会自动覆盖它。因此没有梯度累积时，也必须在合适的时机调用 `zero_grad()`。把它漏掉是初学者最常见的 bug 之一。

## 4. Batch Size：一次让模型看多少条数据

### 4.1 定义与直觉

`batch_size` 是一个 mini-batch 中的样本数。例如训练集有 1,000 条样本，`batch_size=100`，则一个 epoch 大约有 10 个 iteration。

~~~python
train_loader = DataLoader(train_dataset, batch_size=32, shuffle=True)
~~~

对单个样本 $i$ 的损失记为 $l_i$。一个 batch 中有 $B$ 个样本时，常见的平均损失是：

~~~text
L_batch = (l_1 + l_2 + ... + l_B) / B
~~~

模型用这个 batch 的平均梯度来近似全体训练数据的梯度。batch 越大，这个估计通常越平滑；batch 越小，估计中的随机波动通常越大。

### 4.2 小 batch 与大 batch 的取舍

| 维度 | 较小 batch | 较大 batch |
| --- | --- | --- |
| 显存占用 | 较低 | 较高，可能 OOM |
| 单步梯度噪声 | 较大 | 较小、更平滑 |
| 每个 epoch 的 iteration 数 | 较多 | 较少 |
| GPU 利用率 | 可能偏低 | 常更高，但会饱和 |
| 每个 optimizer step 的速度 | 通常较快 | 通常较慢 |
| 泛化表现 | 有时受益于适度噪声 | 并非天然更好 |

“大 batch 一定更好”是错误的。它能改善吞吐，但需要更多显存，也常常需要一起重新调整学习率和训练步数。对于大模型，序列长度、激活值和优化器状态往往比参数本身更容易把显存撑满。

### 4.3 在语言模型中要额外关心 token 数

文本任务的每个样本长度不一。`batch_size=8` 不代表每个 batch 的计算量固定：8 条长度 128 的文本与 8 条长度 2,048 的文本相差很大。语言模型训练常用的更准确指标是：

~~~text
每次参数更新的有效 token 数
= 每卡 batch size × 序列长度 × GPU 数 × 梯度累积步数
~~~

为了减少 padding 浪费，真实项目还会按长度分桶（bucketing）或设置 token-based batch。刚开始学习时，先把最大长度固定，建立稳定基线即可。

### 4.4 如何选择起点

没有通用最优值。一个保守做法是：

1. 先用一个能稳定运行的较小值，例如图像/表格任务取 16 或 32，文本微调常从每卡 1、2、4 开始。
2. 记录显存峰值、每秒样本数、loss 和验证指标。
3. 在不 OOM 的前提下逐步增大，例如 16 -> 32 -> 64；每次只改一个量。
4. batch 改动明显时，重新搜索学习率，而不是沿用旧值。

`nvidia-smi` 能观察 GPU 显存与利用率。不要只看显存没有满就盲目增大 batch：当吞吐提升已经很小，增大 batch 的收益可能不足以抵消调参成本。

## 5. 学习率：每次参数更新迈多大步

### 5.1 它控制什么

学习率（learning rate，常写作 `lr` 或 $\eta$）决定参数沿负梯度方向移动的尺度：

~~~text
θ <- θ - η × ∇θL
~~~

在 PyTorch 中，学习率通常交给优化器：

~~~python
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
~~~

这里的 `3e-4` 是科学计数法，等于 `0.0003`。学习率不是模型“学习速度”的唯一因素，但它往往是最敏感的超参数。

### 5.2 过大、合适、过小分别像什么

| 情况 | 训练现象 | 常见处理 |
| --- | --- | --- |
| 学习率过大 | loss 剧烈震荡、突然变为 NaN/Inf、验证指标恶化 | 降低学习率；检查数据、混合精度与梯度裁剪 |
| 大致合适 | 训练 loss 总体下降，允许有少量批间波动；验证指标改善 | 作为基线继续训练或小范围搜索 |
| 学习率过小 | loss 很平稳但几乎不下降，训练进展极慢 | 逐步提高学习率或增加训练步数 |

不要只盯着最后一个 loss。应画出或记录移动平均的训练 loss，并定期看验证集指标。训练 loss 一直下降而验证集变差通常是过拟合，不应简单靠增大学习率解决。

### 5.3 为什么 batch size 变化常需联动学习率

更大的 batch 让每步梯度的随机性变小，但同一个 epoch 中的参数更新次数也变少。例如 3,200 条数据：

| batch size | 每个 epoch 的 step 数 |
| --- | --- |
| 32 | 100 |
| 128 | 25 |

如果把 batch 从 32 增大到 128，却保持 epoch 数和学习率不变，模型在一个 epoch 内只更新原来的四分之一次数，训练轨迹会变。常见的经验是**线性缩放规则**：batch 放大 $k$ 倍，尝试把学习率也放大约 $k$ 倍；但这只是搜索起点，不是定律，尤其对 AdamW、预训练模型微调和短训练都需要实测。

安全的实践是：先固定一个可复现实验，再围绕原始学习率做对数尺度搜索，例如 `1e-5`、`3e-5`、`1e-4`、`3e-4`，一次只运行少量实验并比较同一验证指标。

### 5.4 预热和调度器

训练一开始模型参数、优化器动量和混合精度状态都还不稳定。学习率预热（warmup）会在开始的若干 optimizer step 内从很小的值逐渐升到目标学习率。之后再随训练推进下降，常见策略包括余弦退火和线性衰减。

关键点：调度器通常应按**optimizer step**而不是按 DataLoader iteration 前进。使用梯度累积时，每积累完一组梯度、真正更新一次参数后再调用 `scheduler.step()`。

~~~python
optimizer.step()
scheduler.step()  # 与实际参数更新保持一一对应
~~~

## 6. 梯度裁剪：给异常大的更新加上安全阀

### 6.1 它解决什么问题

深层网络、长序列、异常样本或不合适的学习率可能产生非常大的梯度。一次过大的参数更新会让 loss 爆炸、出现 `inf` 或 `nan`，之后训练通常难以恢复。梯度裁剪（gradient clipping）在更新前限制梯度大小，避免单次更新失控。

最常用的是按全局 L2 范数裁剪：

~~~text
如果 ||g|| <= max_norm：保持 g 不变
如果 ||g|| >  max_norm：使用 g × max_norm / ||g||
~~~

它保留梯度方向，只缩小长度。PyTorch 写法：

~~~python
grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
~~~

返回值 `grad_norm` 是裁剪前的总梯度范数，适合记录到日志中。`max_norm=1.0` 是常见起点，不是对所有任务都最优。

### 6.2 正确位置

梯度裁剪一定发生在：

~~~text
backward() 之后 -> optimizer.step() 之前
~~~

~~~python
loss.backward()
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
optimizer.step()
~~~

以下写法没有意义，因为梯度还没有产生：

~~~python
# 错误：此时 parameter.grad 通常仍是 None
clip_grad_norm_(model.parameters(), max_norm=1.0)
loss.backward()
~~~

### 6.3 裁剪不是“修好训练”的万能药

梯度裁剪能限制单次损害，但不会修复根因。若大部分 step 都在强烈裁剪，优先检查：

- 学习率是否过大；
- 输入特征或标签是否有 NaN、Inf、极端异常值；
- 损失函数和标签类型/取值范围是否匹配；
- 模型初始化、归一化、序列长度和数据预处理是否正确；
- 是否忘记了 `optimizer.zero_grad()`，导致非预期的跨 step 梯度叠加。

可以把梯度范数与训练 loss 一同记录。偶发尖峰不一定异常；持续远高于阈值才是强信号。

### 6.4 value clipping 与 norm clipping

还有 `torch.nn.utils.clip_grad_value_`，它把每个单独梯度元素截到某个区间。对初学者和多数 Transformer 微调任务，优先理解并尝试 `clip_grad_norm_`：它更符合“限制整体更新尺度”的直觉。不要同时启用两种裁剪，除非你明确知道理由。

## 7. 梯度累积：用多次小 batch 模拟一次大 batch

### 7.1 为什么需要它

GPU 显存不足时，可能只能放下 `batch_size=2`，但你希望每次参数更新使用大约 16 个样本的信息。梯度累积（gradient accumulation）让模型连续处理 8 个小 batch，只做一次参数更新。

~~~text
微批量（micro-batch）大小 = 2
累积步数（accumulation steps） = 8
有效 batch size（effective batch size） = 2 × 8 = 16
~~~

多 GPU 数据并行时还要乘 GPU 数量：

~~~text
有效 batch size = 每卡 micro-batch × 累积步数 × GPU 数
~~~

### 7.2 最关键的一行：先除以累积步数

假设损失默认是 batch 内平均值。要让累积 8 次的梯度规模接近一个大 batch 的平均梯度，必须在反向传播前把 loss 除以 8：

~~~python
loss = loss / accumulation_steps
loss.backward()
~~~

若漏掉这一步，累计梯度会大约放大 8 倍，效果相当于把学习率意外放大，容易造成不稳定或 NaN。

完整骨架如下：

~~~python
accumulation_steps = 4
optimizer.zero_grad(set_to_none=True)

for batch_index, (inputs, labels) in enumerate(train_loader):
    logits = model(inputs)
    loss = criterion(logits, labels) / accumulation_steps
    loss.backward()

    should_step = (batch_index + 1) % accumulation_steps == 0
    if should_step:
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)
~~~

### 7.3 最后不足一组 batch 的情况

上面的简化代码假定一个 epoch 的 batch 数能被 `accumulation_steps` 整除。真实训练中最后一组常常不满：若不额外处理，最后几个 batch 的梯度可能没有被更新。

入门时有两个清晰选择：

- 训练数据允许丢弃尾部时，DataLoader 设为 `drop_last=True`，并使每 epoch 的 iteration 数可被累积步数整除。
- 不允许丢数据时，在循环结束后检查是否还有未更新的累积梯度，并做一次补充 `step()`；更严格的实现还要按最后实际累积的批次数重新缩放损失。

文末完整示例使用第一种方式，目的在于把机制讲清楚。生产训练应明确处理尾组而不是依赖偶然整除。

### 7.4 它与真正大 batch 完全相同吗

不完全。它们在“累计梯度再更新”的数学目标上接近，但仍可能因以下因素产生差异：

- Dropout 等随机层会在每个微批量重新采样；
- BatchNorm 会分别使用每个微批量的统计量；
- 数据增强、动态 padding、分布式通信和浮点舍入会造成差异；
- 每次微批量仍要做一次前向和反向传播，因此吞吐不必然与真实大 batch 一样好。

对 Transformer 常见的 LayerNorm，梯度累积通常非常实用；对强依赖 BatchNorm 的小模型则应更谨慎。

## 8. 混合精度训练：用合适的数值格式换显存和速度

### 8.1 FP32、FP16 与 BF16

默认的 FP32（32 位浮点数）数值范围和精度都较好，但显存和计算成本更高。混合精度训练（automatic mixed precision，AMP）让适合低精度的算子使用 FP16 或 BF16，同时保留需要稳定性的关键操作在更高精度下执行。

| 格式 | 位数 | 优点 | 主要风险/特点 |
| --- | --- | --- | --- |
| FP32 | 32 | 稳定、范围大 | 显存占用和带宽成本高 |
| FP16 | 16 | 在支持 Tensor Core 的 GPU 上通常很快、节省显存 | 数值范围较小，梯度可能下溢，需要损失缩放 |
| BF16 | 16 | 指数范围接近 FP32，通常更不易溢出/下溢 | 尾数精度低于 FP32，需要硬件支持 |

“混合”不等于把所有数字都强制改为 16 位。PyTorch 的自动混合精度会根据算子选择合适精度，这比手动把整个模型和输入都 `.half()` 更稳妥。

### 8.2 autocast 与 GradScaler 各做什么

AMP 有两个容易混淆的组件：

- `torch.autocast`：包裹**前向传播和损失计算**，自动选择许多算子的执行精度。
- `GradScaler`：主要用于 **FP16**。它先放大 loss，再反向传播，让很小的梯度不至于因 FP16 表示范围有限而变成 0；更新前再还原梯度尺度。

概念顺序：

~~~text
autocast 下前向计算 -> 得到 loss
-> GradScaler 放大 loss -> backward
-> unscale_ 还原梯度 -> （可选）裁剪梯度
-> scaler.step(optimizer) -> scaler.update()
~~~

使用 FP16 和梯度裁剪时，`unscale_` 必须在裁剪之前。否则你裁剪的是被放大后的梯度，阈值失去原本含义。

~~~python
scaler.scale(loss).backward()
scaler.unscale_(optimizer)  # 先还原真实梯度尺度
clip_grad_norm_(model.parameters(), max_norm=1.0)
scaler.step(optimizer)
scaler.update()
~~~

### 8.3 什么时候启用

通常只在 CUDA GPU 上启用 AMP。CPU 上可以先使用纯 FP32，保证代码、数据和指标正确；验证无误后再启用 GPU AMP。较新的 NVIDIA GPU 上，BF16 往往是很稳健的选择；如果硬件不支持 BF16，使用 FP16 加 `GradScaler`。

AMP 不是为了掩盖数值错误。若禁用 AMP 后仍然 NaN，优先检查学习率、数据和损失函数。若只在 FP16 下 NaN，检查是否正确使用了 `GradScaler`、是否漏掉 `unscale_`、是否有特别大的激活或损失。

## 9. 把五项放在一起：一张关系图

~~~text
每卡 micro-batch ─┐
梯度累积步数      ├─> 有效 batch size ─> 梯度估计的噪声、每 epoch 更新次数
GPU 数量          ─┘                         │
                                                 └─> 需要重新评估学习率与调度器步数

学习率 ────────────────────────────────────────> 单次参数更新的基本尺度
梯度裁剪 ──────────────────────────────────────> 约束异常大的单次更新
混合精度 ──────────────────────────────────────> 降低显存/提高吞吐；FP16 要处理数值尺度
~~~

建议的调参顺序：

1. 先用 FP32、小模型或小数据集跑通，确认 loss 能下降。
2. 找到不 OOM 的 micro-batch，并记录吞吐与显存。
3. 固定 batch，先粗略搜索学习率。
4. 有梯度尖峰或不稳定证据时加入梯度裁剪并记录梯度范数。
5. 显存限制有效 batch 时加入梯度累积，重新确认实际 optimizer step 数。
6. 最后启用 AMP，比较显存、速度和验证指标；确认 FP16 的缩放和裁剪顺序。

一次只改变一个变量。比如同时把 batch 从 8 改为 64、学习率从 `1e-4` 改为 `1e-3`，再启用 AMP，训练变好或变坏时都无法知道原因。

## 10. 可运行完整示例：二分类训练循环

这个示例人为生成二维二分类数据，模型是一个很小的全连接网络。它的价值不在模型效果，而在于演示训练循环中五项机制的正确位置。代码在 CPU 上可运行；有 CUDA GPU 时会自动启用 BF16 或 FP16 AMP。

安装 PyTorch 请按你的操作系统和 CUDA 版本参照 [PyTorch 官网](https://pytorch.org/get-started/locally/) 的命令。不要在不了解 CUDA 版本的情况下随意复制第三方安装命令。

~~~python
import math

import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset


def create_dataset(sample_count: int = 2_048) -> TensorDataset:
    """创建一个可分但带少量噪声的二维二分类数据集。"""
    generator = torch.Generator().manual_seed(42)
    features = torch.randn(sample_count, 2, generator=generator)
    boundary = features[:, 0] * 1.2 - features[:, 1] * 0.8
    labels = (boundary + 0.25 * torch.randn(sample_count, generator=generator) > 0)
    return TensorDataset(features, labels.to(torch.float32).unsqueeze(1))


class BinaryClassifier(nn.Module):
    """用于演示训练循环的简单二分类网络。"""

    def __init__(self) -> None:
        super().__init__()
        self.layers = nn.Sequential(
            nn.Linear(2, 32),
            nn.ReLU(),
            nn.Linear(32, 1),
        )

    def forward(self, features: torch.Tensor) -> torch.Tensor:
        """根据二维特征返回未经过 sigmoid 的分类 logits。"""
        return self.layers(features)


torch.manual_seed(42)
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

# 这里的 32 是每次真正放入设备的 micro-batch，不是有效 batch。
micro_batch_size = 32
accumulation_steps = 4
# 因此单卡有效 batch size = 32 × 4 = 128。
effective_batch_size = micro_batch_size * accumulation_steps
learning_rate = 3e-4
max_grad_norm = 1.0
epoch_count = 10

# 2,048 / 32 = 64，64 可以被 4 整除，便于本示例聚焦核心逻辑。
loader = DataLoader(
    create_dataset(),
    batch_size=micro_batch_size,
    shuffle=True,
    drop_last=True,
)
model = BinaryClassifier().to(device)
criterion = nn.BCEWithLogitsLoss()
optimizer = torch.optim.AdamW(model.parameters(), lr=learning_rate)

# CUDA 上优先 BF16；硬件不支持时回退到 FP16。
amp_enabled = device.type == "cuda"
amp_dtype = torch.bfloat16
if amp_enabled and not torch.cuda.is_bf16_supported():
    amp_dtype = torch.float16

# FP16 需要损失缩放；BF16 通常不需要。enabled=False 时它是安全的空操作。
scaler = torch.amp.GradScaler(
    "cuda",
    enabled=amp_enabled and amp_dtype == torch.float16,
)

print(
    f"device={device}, micro_batch={micro_batch_size}, "
    f"effective_batch={effective_batch_size}, amp={amp_enabled}, dtype={amp_dtype}"
)

for epoch in range(epoch_count):
    model.train()
    optimizer.zero_grad(set_to_none=True)
    epoch_loss_sum = 0.0
    correct_count = 0
    sample_count = 0
    update_count = 0
    last_grad_norm = math.nan

    for batch_index, (features, labels) in enumerate(loader):
        features = features.to(device)
        labels = labels.to(device)

        # autocast 只包住前向传播和 loss 计算。
        with torch.autocast(
            device_type=device.type,
            dtype=amp_dtype,
            enabled=amp_enabled,
        ):
            logits = model(features)
            batch_loss = criterion(logits, labels)
            # 必须除以累积步数，保证累积梯度的尺度正确。
            loss = batch_loss / accumulation_steps

        # FP16 时 scale；其余情况直接 backward，统一通过 scaler 调用即可。
        scaler.scale(loss).backward()

        with torch.no_grad():
            predictions = (torch.sigmoid(logits) >= 0.5).to(labels.dtype)
            correct_count += (predictions == labels).sum().item()
            sample_count += labels.numel()
            epoch_loss_sum += batch_loss.item() * labels.size(0)

        should_step = (batch_index + 1) % accumulation_steps == 0
        if should_step:
            # FP16 梯度经过放大；裁剪前必须恢复到真实尺度。
            scaler.unscale_(optimizer)
            last_grad_norm = torch.nn.utils.clip_grad_norm_(
                model.parameters(),
                max_norm=max_grad_norm,
            ).item()
            scaler.step(optimizer)
            scaler.update()
            optimizer.zero_grad(set_to_none=True)
            update_count += 1

    mean_loss = epoch_loss_sum / sample_count
    accuracy = correct_count / sample_count
    print(
        f"epoch={epoch + 1:02d} loss={mean_loss:.4f} "
        f"accuracy={accuracy:.3f} updates={update_count} "
        f"last_grad_norm={last_grad_norm:.3f}"
    )
~~~

运行后，loss 应总体下降，accuracy 应逐步升高。不同 PyTorch、CPU/GPU 和硬件产生的具体数字会不同，不应把某一行精确输出当作唯一正确答案。

### 10.1 逐段核对示例

- `BCEWithLogitsLoss` 接受原始 logits，所以模型末层没有 `Sigmoid`。评估准确率时才用 `torch.sigmoid` 转为概率。
- `batch_loss` 用于日志，是未缩放的真实 batch loss；`loss` 是除以累积步数后用于反向传播的 loss。
- `scaler.scale(loss).backward()` 在 scaler 未启用时相当于普通 `loss.backward()`，因此可共用一条代码路径。
- `scaler.unscale_(optimizer)` 放在梯度裁剪前，使 `max_grad_norm=1.0` 仍表示真实梯度的阈值。
- 只有 `should_step` 为真时才更新参数、更新 scaler、清空梯度。调度器若加入，也应放在这个分支中。
- 这个例子通过 `drop_last=True` 和可整除的数据量避开尾组问题；不要把这个简化忘记带到真实项目中。

## 11. 三个小实验：把概念变成观察

请每次只改一处，运行相同 epoch 数，并记录 `loss`、`accuracy`、总耗时和 GPU 显存峰值。

### 实验 A：观察 batch size

依次设置 `micro_batch_size = 8`、`32`、`128`；临时设 `accumulation_steps = 1`。问题：每个 epoch 的更新次数是否改变？loss 的批间波动是否改变？吞吐是否线性增长？

### 实验 B：观察学习率

固定 batch，分别设置 `learning_rate = 1e-5`、`3e-4`、`1e-2`。问题：哪个值下降太慢？哪个值可能震荡？若 `1e-2` 出现 NaN，先把它调小，而不是首先依赖裁剪。

### 实验 C：观察梯度累积

比较以下两组，理论有效 batch 都是 128：

| 方案 | micro-batch | accumulation steps | 每 epoch 参数更新数 |
| --- | ---: | ---: | ---: |
| 方案 1 | 128 | 1 | 较少 |
| 方案 2 | 32 | 4 | 相同 |

在显存允许时比较两者的 loss 曲线与运行时间。然后故意删除 `loss = batch_loss / accumulation_steps` 中的除法，观察训练稳定性变化，再立即恢复。这个实验能帮助你理解“累积”不是只把 `step()` 延后。

## 12. 高频故障排查手册

### 12.1 CUDA Out of Memory（OOM）

按风险最小的顺序尝试：

1. 确认没有把整个数据集或历史输出意外放到 GPU。
2. 降低 micro-batch，而不是先降低有效 batch；需要时提高梯度累积步数。
3. 减少文本最大序列长度。注意 Attention 的开销会随序列长度明显增加。
4. 使用 AMP，优先评估 BF16，或用 FP16 + GradScaler。
5. 检查是否无意保留了计算图，例如把带梯度的 `loss`、`logits` 长期 append 到列表；日志通常使用 `.item()` 或 `.detach()`。
6. 确认验证阶段使用 `model.eval()` 和 `torch.no_grad()`。

不要在每个 iteration 中反复调用 `torch.cuda.empty_cache()` 试图“修复”真实 OOM。它可能影响性能，且不能替代降低峰值显存。

### 12.2 loss 变为 NaN 或 Inf

先定位，而不是连续叠加补丁：

~~~python
if not torch.isfinite(loss):
    raise RuntimeError(f"检测到非有限 loss: {loss.item()}")
~~~

排查顺序：

1. 用 FP32、较小学习率和很小数据集复现，排除 AMP 变量。
2. 检查输入特征、标签、模型输出和 loss 是否都为有限值。
3. 检查损失函数的输入约定，例如 `CrossEntropyLoss` 接收类别索引和 logits，`BCEWithLogitsLoss` 接收 float 标签和 logits。
4. 观察梯度范数；确认没有忘记梯度清零或错误放大梯度累积。
5. 再启用 AMP；FP16 时确认 `GradScaler`、`unscale_` 和裁剪顺序。

### 12.3 loss 不下降或参数根本没更新

逐项验证：

- 模型是否处在 `model.train()`；验证时才应 `model.eval()`。
- `loss.backward()` 是否实际执行；参数的 `requires_grad` 是否为 `True`。
- `optimizer` 是否接收了你正在训练的模型参数。
- 是否遗漏 `optimizer.step()`，或梯度累积条件使它从未满足。
- 是否在 `step()` 前错误调用了 `zero_grad()`。
- 数据与标签是否错位，类别编码是否正确，训练集是否真的有可学习信号。

可以在一次更新前后比较一个参数：

~~~python
parameter = next(model.parameters())
before = parameter.detach().clone()
# 执行 backward、裁剪与 optimizer.step()
changed = not torch.equal(before, parameter.detach())
print(f"参数是否改变：{changed}")
~~~

这只能证明参数是否变化，不能证明训练逻辑正确；仍要看 loss 和验证指标。

### 12.4 训练 loss 下降，验证集却变差

这更像过拟合、验证流程错误或数据泄漏检查不足，而不是 batch size 或 AMP 的直接错误。优先核对训练/验证划分、`model.eval()`、验证时的 `no_grad()`，再考虑更多数据、正则化、早停、数据增强或减少训练轮数。

## 13. 初学者常见误区

| 误区 | 更准确的理解 |
| --- | --- |
| batch 越大越好 | 大 batch 是显存、吞吐、优化和泛化之间的取舍 |
| 学习率越大学得越快 | 过大的步长会直接跨过低损失区域，导致震荡或发散 |
| 梯度裁剪应放在哪里都可以 | 必须在反向传播后、参数更新前；FP16 先反缩放 |
| 梯度累积就是少调用几次 `step()` | 还必须按累积步数缩放 loss，并处理尾组 |
| 开 AMP 一定更快且结果完全相同 | 速度取决于硬件和算子；数值路径存在小差异，必须复验指标 |
| AMP 下把模型强制 `.half()` 就够了 | 推荐 `autocast`；FP16 还需要正确的损失缩放逻辑 |
| loss 下降就说明模型可用 | 还要用独立验证集、目标业务指标和边界样本验证 |

## 14. 一份可复用的训练前检查清单

开始一次新实验前，逐项确认：

- [ ] 数据集大小、类别分布、输入形状、标签类型和取值范围已检查。
- [ ] 固定或记录随机种子、代码版本、数据版本和超参数。
- [ ] 明确记录 micro-batch、累积步数、GPU 数量和有效 batch size。
- [ ] 明确学习率、优化器、权重衰减、训练 epoch 和总 optimizer step 数。
- [ ] 梯度累积时，loss 已按累积步数缩放，且尾组策略明确。
- [ ] 梯度裁剪位于 `backward()` 后、`step()` 前；FP16 先 `unscale_`。
- [ ] AMP 的设备、dtype 与 `GradScaler` 启用条件正确。
- [ ] 训练和验证模式切换正确，验证过程不构建计算图。
- [ ] 日志至少包含训练 loss、验证指标、学习率、梯度范数、显存和异常信息。

## 15. 下一步学习路线

掌握本篇后，可以按这个顺序继续：

1. 用 `Dataset` 和 `DataLoader` 读取一个真实公开数据集，补充训练/验证划分。
2. 学习 Adam、AdamW、weight decay、学习率 warmup 与 cosine decay 的差异。
3. 给训练循环加入 checkpoint 保存、恢复训练、最佳验证指标保存和 TensorBoard 日志。
4. 学习 Transformer 的 tokenization、attention mask、序列长度与 token 级有效 batch。
5. 再尝试 Hugging Face Transformers 的微调脚本，逐项对照它的 `per_device_train_batch_size`、`gradient_accumulation_steps`、`fp16/bf16`、`max_grad_norm` 与本篇概念。

真正的掌握标准不是背出定义，而是能够在一次训练异常时回答：当前的**有效 batch 是多少**、本 epoch 实际更新了多少次、学习率在第几个 update 是多少、梯度是否持续被裁剪、AMP 用的是什么 dtype，以及证据记录在哪里。
