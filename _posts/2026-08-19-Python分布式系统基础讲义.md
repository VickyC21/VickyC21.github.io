# Python 分布式系统基础讲义

> 面向大模型开发工程师初学者。本讲义不要求你先会 Kubernetes、Kafka 或微服务框架；目标是先建立正确的问题意识，再通过 Python 服务场景理解常见方案。示例用于学习核心机制，生产环境还需要安全、监控、容量规划和故障演练。

## 1. 学习目标

完成本讲义后，你应能回答：

- 为什么单机程序部署成多个实例后会出现新问题。
- 服务实例的地址变化时，调用方如何找到它。
- 一次请求如何被分配到多个实例，以及“均匀”不等于“合适”。
- 分布式系统中的“一致”到底在保证什么。
- 数据库和缓存同时存在时，为什么会读到旧值。
- 消息队列解决了什么，为什么消费端必须接受重复消息。
- 网络超时后为什么不能简单重试，以及怎样避免重复扣费或重复执行任务。

## 2. 贯穿全文的场景

假设你正在开发企业知识库问答服务：

~~~text
浏览器 / SDK
    |
API 网关
    |
多个 Python API 实例
    |                 \
PostgreSQL             Redis
用户、权限、任务记录    缓存、限流、短期状态
    |
消息队列
    |
多个异步 Worker
    |
文档解析、向量化、调用模型、写回结果
~~~

初期只有一个 FastAPI 进程时，数据都在本机内存，调用只会失败或成功。上线后增加多个实例，系统必须面对这些事实：

1. 实例会扩容、重启、迁移，IP 和端口不再固定。
2. 任意网络调用都可能超时，但超时不等于对方没有成功。
3. 多个实例会并发修改同一份数据。
4. 某台机器、某个依赖、某条网络链路会暂时不可用。
5. 请求可能比下游处理得更快，系统需要排队、限速或降级。

分布式系统不是“把程序拆成很多服务”本身，而是在不可靠网络和多副本并发下，仍然让系统行为可理解、可恢复、可验证。

## 3. 六个总原则

| 原则 | 白话解释 | 对 LLM 服务的意义 |
| --- | --- | --- |
| 网络不可靠 | 请求可能丢失、延迟、重复或乱序 | 模型调用超时后，不能断言没有扣费或没有生成 |
| 部分失败常态化 | 一个组件坏了，不代表全系统都坏 | 向量库异常时不能拖垮 API |
| 状态是昂贵资源 | 跨实例共享状态会带来同步问题 | 对话状态、任务状态必须有明确存储位置 |
| 超时不是失败证明 | 客户端等不到响应，不等于服务端没执行 | 写操作需要幂等设计 |
| 至少一次很常见 | 消息和请求会重复到达 | Worker 要能安全重复消费 |
| 可观测性是功能 | 没有日志和指标，就无法判断发生了什么 | 每次请求都应有 trace_id、耗时和错误分类 |

## 4. 最小实验环境

以下命令可启动学习用 Redis 和 PostgreSQL。它们不是生产配置，但足够支持后面的概念练习。

~~~bash
docker run --name distributed-redis -p 6379:6379 -d redis:7-alpine

docker run --name distributed-postgres \
  -e POSTGRES_PASSWORD=study \
  -e POSTGRES_DB=study \
  -p 5432:5432 \
  -d postgres:16-alpine
~~~

Python 示例常用依赖：

~~~bash
python -m pip install fastapi "uvicorn[standard]" httpx redis sqlalchemy psycopg[binary]
~~~

为所有请求生成并传递追踪 ID。它不是分布式协议，却是排障的起点。

~~~python
from uuid import uuid4

from fastapi import FastAPI, Request
from starlette.middleware.base import BaseHTTPMiddleware

app = FastAPI()


class TraceIdMiddleware(BaseHTTPMiddleware):
    """为请求补充可跨服务传播的追踪标识。"""

    async def dispatch(self, request: Request, call_next):
        trace_id = request.headers.get("X-Trace-Id", str(uuid4()))
        response = await call_next(request)
        response.headers["X-Trace-Id"] = trace_id
        return response


app.add_middleware(TraceIdMiddleware)
~~~

生产中还应把 trace_id 写入结构化日志，并在调用下游服务和发送消息时继续携带它。

## 5. 服务发现：调用方怎样找到活着的服务

### 5.1 问题是什么

服务发现解决的是“服务名如何变成可连接地址”。

不要把服务地址硬编码为 "http://10.0.0.8:8000"。一旦实例重启、扩缩容或故障迁移，这个地址就会失效。调用方更应依赖稳定的服务名，例如 "embedding-service"，再由发现机制得到当前可用实例列表。

~~~text
调用方请求 embedding-service
        |
服务发现系统返回：
- 10.0.1.12:8000
- 10.0.1.15:8000
- 10.0.1.19:8000
        |
调用方或代理选择其中一个实例
~~~

### 5.2 常见方式

| 方式 | 典型环境 | 优点 | 主要限制 |
| --- | --- | --- | --- |
| 静态配置 | 本地开发、极小系统 | 最简单 | 实例变化要人工改配置 |
| DNS | 容器平台、云环境 | 标准、低心智负担 | DNS 缓存和健康语义有限 |
| 注册中心 | Consul、Nacos、Eureka | 可注册、查询、健康检查 | 多了一个关键基础设施 |
| Kubernetes Service | K8s 集群 | 服务名和负载均衡集成 | 需要理解 K8s 网络模型 |
| 服务网格 | Istio 等 | 流量治理能力强 | 复杂度高，初学阶段不必先上 |

对初学者最重要的结论：业务代码通常只使用服务名；实例列表、健康检查和流量切换由平台或基础设施承担。

### 5.3 健康检查：存活不等于可接流量

健康检查常分两类：

- 存活检查（liveness）：进程是否卡死，失败后平台可以重启它。
- 就绪检查（readiness）：实例是否已经能安全接收流量，失败后平台应把它从负载均衡池移除。

模型服务刚启动时可能仍在加载权重。此时进程活着，但不应该接收真实请求。

~~~python
from fastapi import FastAPI, HTTPException

app = FastAPI()
model_ready = False


@app.get("/live")
async def live() -> dict[str, str]:
    """表示进程仍可响应；不要在这里做昂贵依赖检查。"""
    return {"status": "alive"}


@app.get("/ready")
async def ready() -> dict[str, str]:
    """只有本实例可安全处理请求时才返回成功。"""
    if not model_ready:
        raise HTTPException(status_code=503, detail="模型尚未加载完成")
    return {"status": "ready"}
~~~

误区：把数据库、Redis、模型服务全部在存活检查中串行调用。这样短暂依赖抖动会引发大规模重启，反而扩大事故。应根据组件特性设计就绪条件，并为依赖故障准备降级行为。

### 5.4 注册、摘除和陈旧实例

若使用注册中心，实例启动时注册，退出前注销，或定期发送心跳。现实中“正常注销”并不可靠：机器断电、网络分区时注册中心收不到注销请求。因此还要有租约或心跳超时，使陈旧实例最终被剔除。

超时时间太长，故障实例下线慢；太短，短暂网络抖动可能误杀健康实例。没有万能数字，应通过监控和演练调整。

## 6. 负载均衡：请求应交给哪一个实例

### 6.1 两层位置

负载均衡可发生在：

- 客户端侧：客户端从实例列表中挑选一个地址。
- 服务端侧：客户端只访问一个统一入口，由反向代理、负载均衡器或平台转发。

在多数 Web 和 LLM 应用中，优先让网关、Ingress、Kubernetes Service 或云负载均衡承担通用流量分发；业务代码不应自行维护复杂的实例管理。

### 6.2 常见算法

| 算法 | 做法 | 适用情形 | 风险 |
| --- | --- | --- | --- |
| 轮询 | 按顺序轮流分配 | 实例能力接近 | 忽略请求耗时差异 |
| 加权轮询 | 能力强的实例分更多请求 | CPU/GPU 配置不同 | 权重需维护 |
| 最少连接 | 选择连接数少的实例 | 长连接、耗时差异大 | 连接数不等于真实负载 |
| 最少请求 / EWMA | 参考在途请求与延迟 | 高延迟服务 | 需要可靠指标 |
| 一致性哈希 | 相同 key 尽量落到同一实例 | 缓存、会话亲和 | 不能替代共享状态设计 |
| 随机二选一 | 随机选两个，取更空闲的 | 分布式调度常用 | 依赖负载数据 |

模型推理请求成本差异很大。短问题和长上下文、长输出请求不应被简单看成同等负载。生产推理系统还会考虑 token 数、KV Cache、GPU 显存和队列长度。

### 6.3 一致性哈希的直觉

普通 hash 取模中，实例数从 3 变为 4 时，很多 key 的映射都会改变，缓存命中率会突然下降。一致性哈希把节点与 key 放到一个环上，key 顺时针找到第一个节点；增加或移除一个节点时，主要迁移它相邻区间的 key。

~~~text
hash 环：
节点 A -------- 节点 B -------- 节点 C
       key-1 -> B
       key-2 -> C

新增节点 D 主要接管相邻区间的一部分 key，
而不是让所有 key 重新映射。
~~~

真实实现通常使用虚拟节点，让实例在环上分布更均匀。初学阶段只需理解：它是“减少成员变化导致的大面积重映射”的策略，不是分布式一致性协议。

### 6.4 会话粘滞与无状态服务

有些负载均衡器支持会话粘滞：同一用户尽量固定到同一个实例。它能临时解决“会话放在内存里”的问题，但实例故障、扩缩容和多机房时仍会丢状态。

更稳妥的默认方案是：

- API 实例尽量无状态。
- 用户会话、任务状态、限流计数放入 Redis 或数据库。
- 临时文件、模型权重、配置放在共享的可靠存储或镜像中。

## 7. 一致性：多个副本怎样看待同一份事实

### 7.1 不要把“一致性”当成单一概念

| 层面 | 要解决的问题 | 示例 |
| --- | --- | --- |
| 数据约束一致性 | 一次事务后数据仍满足规则 | 账户余额不能变成负数 |
| 副本一致性 | 多个副本何时看到相同数据 | 主库写入后只读副本何时可读到 |
| 并发一致性 | 并发操作是否像按某顺序执行 | 两人同时抢最后一个名额 |
| 缓存一致性 | 缓存与数据库何时可能不同 | 用户改昵称后仍读到旧昵称 |
| 业务一致性 | 跨服务步骤最终是否协调 | 创建订单与扣库存的关系 |

### 7.2 强一致与最终一致

强一致可以粗略理解为：一次成功写入后，后续读取不会再看到旧值，表现好像系统只有一个副本。它给使用者更简单的直觉，但通常需要更高协调成本和更高延迟。

最终一致意味着：副本短时间可能不同，但在没有新写入时会逐渐收敛。它常见于缓存、搜索索引、异步消息和跨地域复制。

关键不是“最终一致不好”，而是要明确：

1. 允许旧多久。
2. 谁能看到旧值。
3. 旧值会造成什么业务后果。
4. 用什么机制收敛和补偿。

例如，文档上传后 10 秒内搜索不到新内容可能可接受；支付成功后显示“未支付”通常不可接受。

### 7.3 CAP 的正确入门理解

网络分区指集群成员之间无法通信，或通信慢到无法区分“对方故障”与“网络故障”。发生分区时，分布式系统无法同时无条件保证：

- 一致性（C）：所有读请求得到同一份最新视图。
- 可用性（A）：每个请求都能获得非错误响应。
- 分区容错性（P）：在网络分区时仍继续运行。

真实分布式系统必须面对 P，因此关键问题变成：分区发生时，某个操作宁可拒绝，还是宁可返回可能过时的结果？

不要把 CAP 简化为“系统只能选两个”。日常设计更常关心延迟、数据模型、读写路径、故障范围和业务可接受性。

### 7.4 并发写入：丢失更新问题

假设两个请求都读取到库存为 1，二者都判断可以下单，然后都写回库存为 0。最终看起来库存没有负数，但实际卖出了两件，这就是丢失更新或“检查与写入非原子”的问题。

数据库层可把检查和扣减放进一条原子 SQL：

~~~sql
UPDATE inventory
SET available = available - 1
WHERE sku_id = :sku_id
  AND available > 0;
~~~

应用根据受影响行数判断结果：

- 影响 1 行：扣减成功。
- 影响 0 行：库存不足或商品不存在。

这比“先 SELECT，再在 Python 中判断，再 UPDATE”可靠得多。若一次业务包含多张表修改，应使用数据库事务；若跨多个独立服务，则要考虑事务外盒、补偿、Saga 等模式，不能假装存在全局数据库事务。

### 7.5 乐观锁：检测冲突后重试

对用户资料、提示词配置等冲突较少的数据，可加 version 字段：

~~~sql
UPDATE prompt_template
SET content = :content,
    version = version + 1
WHERE id = :id
  AND version = :expected_version;
~~~

若更新行数为 0，说明有人已先修改。服务端应返回冲突，或重新读取后由业务决定是否重试。乐观锁不是自动解决冲突，它是让冲突显式可见。

### 7.6 顺序与因果

分布式消息不保证天然全局顺序。即使单个分区有顺序，不同分区、重试、异步回调也会让你看到乱序事件。

若业务要求“文档删除后不能再被索引”，应让同一文档的事件按 document_id 分区，或在消费者处检查版本号：只处理不小于当前版本的事件。不要仅依赖“消息先发后到”的直觉。

## 8. 缓存一致性：为什么数据库改了，用户还会看到旧数据

### 8.1 先决定谁是事实来源

对关键业务数据，数据库通常是真实来源（source of truth），缓存只是副本或派生结果。这个边界非常重要：

- Redis 故障时，能否从数据库恢复？
- 缓存过期或被淘汰时，数据是否仍正确？
- 修改数据后，如何让缓存失效或更新？

若回答是否定的，那么你不是在用缓存，而是在把关键数据放进一个需要额外可靠性设计的主存储。

### 8.2 Cache-Aside：最常用的读路径

Cache-Aside 的读逻辑是：先读缓存；未命中时读数据库；将结果写入缓存并返回。

~~~python
import json
from typing import Any

import redis


redis_client = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True)


def get_user_profile(user_id: int) -> dict[str, Any] | None:
    """优先读取缓存，未命中时从数据库加载并回填缓存。"""
    cache_key = f"user:profile:{user_id}"
    cached = redis_client.get(cache_key)
    if cached is not None:
        return json.loads(cached)

    profile = load_user_profile_from_database(user_id)
    if profile is not None:
        redis_client.setex(cache_key, 300, json.dumps(profile))
    return profile
~~~

这里的 "load_user_profile_from_database" 是待实现的数据库查询。注意：并发缓存未命中时，多个请求可能同时回源数据库，后面会讨论缓存击穿。

### 8.3 写路径：先写库，再删缓存

常见且相对稳妥的写法：

~~~text
1. 在数据库事务中更新真实数据并提交。
2. 删除对应缓存 key。
3. 后续读请求缓存未命中，再从数据库回填最新值。
~~~

为什么通常是“删缓存”而不是“更新缓存”？删除操作更容易保持简单，下一次读由统一读路径回填。

~~~python
def update_user_nickname(user_id: int, nickname: str) -> None:
    """先提交数据库更新，再使可能陈旧的缓存失效。"""
    update_user_nickname_in_database(user_id, nickname)
    redis_client.delete(f"user:profile:{user_id}")
~~~

它也不是魔法。数据库更新完成后到缓存删除前，仍可能有读请求取到旧缓存。对大部分用户资料、配置展示这是一小段可接受窗口；对强业务约束则应走数据库强一致读，或设计更严格的版本控制与消息驱动失效。

不要使用“先删缓存，再更新数据库”作为默认方案。若缓存被删后，另一个读请求回填了旧数据库值，而数据库随后才更新，就可能把旧值缓存很久。

### 8.4 缓存三大问题

| 问题 | 现象 | 常见缓解措施 |
| --- | --- | --- |
| 缓存穿透 | 不存在的 key 一直打到数据库 | 缓存空值、参数校验、布隆过滤器 |
| 缓存击穿 | 热 key 过期时大量请求同时回源 | 互斥重建、逻辑过期、请求合并 |
| 缓存雪崩 | 大量 key 同时过期或缓存整体故障 | TTL 加随机抖动、限流、降级、多级缓存 |

空值缓存也必须有短 TTL，否则“刚创建的数据”可能被空结果遮住。对于用户输入的任意 ID，还要先做合法性校验，避免攻击者制造海量无意义 key。

### 8.5 缓存重建锁的边界

对极热 key，可以让一个请求负责回源，其他请求短暂等待或返回旧值。Redis 锁只能减少同一时刻的重复重建，不应把长耗时模型调用放在锁内，也不应忽略锁过期、进程崩溃和重复执行问题。

~~~python
import time


def get_hot_config() -> dict[str, Any]:
    """示意：用短锁限制缓存失效瞬间的并发回源。"""
    cache_key = "config:hot"
    lock_key = f"{cache_key}:rebuild-lock"

    cached = redis_client.get(cache_key)
    if cached is not None:
        return json.loads(cached)

    if redis_client.set(lock_key, "1", nx=True, ex=5):
        try:
            value = load_hot_config_from_database()
            redis_client.setex(cache_key, 60, json.dumps(value))
            return value
        finally:
            redis_client.delete(lock_key)

    time.sleep(0.05)
    cached = redis_client.get(cache_key)
    if cached is not None:
        return json.loads(cached)
    return load_hot_config_from_database()
~~~

这是教学示意。生产中应设置等待上限、记录锁竞争、避免无条件删除不属于自己的锁，并评估返回旧值是否比阻塞更好。

## 9. 消息队列：把“现在必须完成”与“稍后可靠完成”分开

### 9.1 队列解决什么

用户上传大型 PDF 后，解析、切块、嵌入和建索引可能需要数分钟。若 HTTP 请求一直等待：

- 网关和客户端可能超时。
- API 实例被长任务占满。
- 服务重启时任务容易丢失。
- 突发上传会直接压垮系统。

消息队列把工作拆成生产者和消费者：

~~~text
API 收到上传
  -> 保存文档和任务记录（待处理）
  -> 发送 document_uploaded 消息
  -> 立即返回 task_id

Worker 消费消息
  -> 解析文档
  -> 生成向量
  -> 更新任务状态
  -> 确认消息
~~~

这让 API 的职责变成“接收并可靠记录任务”，Worker 的职责变成“异步执行并可扩容”。

### 9.2 先区分队列、事件和任务

| 名称 | 关注点 | 示例 |
| --- | --- | --- |
| 任务队列 | 一项工作由某个 Worker 完成 | 生成文档向量 |
| 事件流 | 已发生的事实，可被多个订阅者消费 | 文档已上传 |
| 延迟队列 | 在未来某个时刻执行 | 10 分钟后检查任务状态 |
| 死信队列 | 多次失败后留存待人工检查 | 无法解析的加密 PDF |

RabbitMQ、Redis Streams、Kafka、SQS、Celery 等工具的细节不同，但先要回答业务语义：消息是否必须持久化？一个还是多个消费者组？是否需要顺序？允许多长延迟？失败后怎样处理？

### 9.3 投递语义：至少一次是常态

消费者通常遵循这样的可靠顺序：

~~~text
1. 收到消息。
2. 执行业务副作用，例如写数据库。
3. 副作用成功后确认消息（ack）。
4. 若 Worker 在确认前崩溃，消息会重新投递。
~~~

因此同一消息可能被执行两次。这叫至少一次投递。它比“消息丢失”更可靠，但把责任交给业务层：消费者必须幂等。

恰好一次（exactly once）不是“开一个配置就得到”的通用能力。它通常只在特定边界、特定事务能力内成立；跨数据库、HTTP 调用和外部模型 API 时，仍要按至少一次来设计。

### 9.4 消费者幂等：重复到达也只产生一次业务结果

让每条消息有稳定的 message_id 或业务幂等键。数据库建唯一约束是可靠的最后防线之一：

~~~sql
CREATE TABLE processed_message (
    consumer_name TEXT NOT NULL,
    message_id TEXT NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (consumer_name, message_id)
);
~~~

消费者在同一个数据库事务中记录“已处理”并写业务数据。若重复消息再次到来，插入唯一键失败，说明已处理过，可安全跳过业务副作用。

~~~python
def process_document_uploaded(message: dict[str, str]) -> None:
    """示意：以数据库唯一约束吸收队列重复投递。"""
    with database_transaction() as connection:
        inserted = insert_processed_message(
            connection=connection,
            consumer_name="index-worker",
            message_id=message["message_id"],
        )
        if not inserted:
            return

        index_document(connection, document_id=message["document_id"])
~~~

若 "index_document" 实际调用外部模型 API，就会更复杂：数据库事务无法包住外部 HTTP 调用。常用方法是把任务状态显式存库、使用可恢复状态机、保存外部请求幂等键，并按阶段重试。

### 9.5 事务外盒：避免“写库成功但消息没发出”

一个经典故障窗口：

~~~text
1. API 写入 document 表，成功。
2. API 准备发送消息时进程崩溃。
3. Worker 永远不知道新文档需要处理。
~~~

反过来，先发消息再写库也可能让 Worker 找不到数据。事务外盒的思路是：在同一个数据库事务中写业务数据和 outbox 事件；独立发布器再可靠地把未发布事件送到消息队列。

~~~text
数据库事务：
- INSERT document (...)
- INSERT outbox_event (event_id, type, payload, status='pending')
- COMMIT

发布器循环：
- 读取 pending 事件
- 发布到消息队列
- 标记为 published
~~~

发布器也可能重复发送，因此消费者依旧需要幂等。Outbox 的价值不是消除重复，而是避免丢事件，并把恢复路径变得可观测。

### 9.6 背压与队列积压

消息队列不是无限容量的“缓冲垫”。当生产速度长期大于消费速度，积压会增长，任务延迟越来越高。

你至少应监控：

- 队列深度或消费者滞后量。
- 最旧消息等待时间。
- 消费成功率、失败率、重试次数。
- Worker 并发、CPU、内存、GPU 利用率。
- 死信队列数量与原因。

扩 Worker 可能有效，但也可能把下游数据库或模型 API 打垮。正确动作取决于瓶颈在哪里：限流、批处理、扩容、降低并发、暂停生产或降级都可能是答案。

## 10. 故障重试：重试的是短暂错误，不是所有错误

### 10.1 为什么“再试一次”会造成事故

短暂网络抖动、连接被重置、服务刚切流时，重试能提高成功率。但对以下情况盲目重试只会放大问题：

- 参数非法、权限不足、业务规则不满足。
- 下游已经过载，重试会制造更高流量。
- 写操作其实已经成功，只是响应在路上丢了。
- 依赖永久故障，所有调用方同时持续重试。

所以重试策略必须同时回答：什么错误可重试、等多久、最多几次、如何避免重复副作用、失败后怎么办。

### 10.2 错误分类

| 结果 | 是否通常重试 | 说明 |
| --- | --- | --- |
| 400、422 参数错误 | 否 | 修请求，不靠重试 |
| 401、403 认证授权失败 | 通常否 | 刷新凭据需单独受控流程 |
| 404 资源不存在 | 通常否 | 除非资源最终会出现且有明确约定 |
| 409 并发冲突 | 视业务而定 | 可能重新读取后重试 |
| 429 限流 | 是，遵守 Retry-After | 降低并发和频率 |
| 500、502、503、504 | 有界重试 | 先确认服务语义与容量 |
| 连接超时、连接重置 | 有界重试 | 写操作须有幂等保护 |

HTTP 状态码只是线索，不是完整策略。对于模型 API，还要结合供应商错误码、账单语义、请求是否已接受等文档设计。

### 10.3 指数退避加随机抖动

若所有客户端在同一时刻失败后都等固定 1 秒再请求，会形成同步重试风暴。更常用的等待形式是：

~~~text
等待时间 = min(最大等待, 基础时间 * 2^第几次尝试) + 随机抖动
~~~

例如基础 0.2 秒，最多 3 次，抖动为 0 到 0.1 秒。重试预算必须有限，并受请求的总超时约束。

~~~python
import asyncio
import random
from collections.abc import Awaitable, Callable
from typing import TypeVar

T = TypeVar("T")


async def retry_transient(
    operation: Callable[[], Awaitable[T]],
    should_retry: Callable[[Exception], bool],
    max_attempts: int = 3,
) -> T:
    """以有限次数和指数退避执行可重试的异步操作。"""
    for attempt in range(1, max_attempts + 1):
        try:
            return await operation()
        except Exception as error:
            if attempt == max_attempts or not should_retry(error):
                raise

            base_delay = 0.2 * (2 ** (attempt - 1))
            jitter = random.uniform(0, 0.1)
            await asyncio.sleep(base_delay + jitter)

    raise RuntimeError("不可达：循环已在成功或异常时退出")
~~~

这段代码仍缺少生产能力：总 deadline、指标、日志、错误类型、取消传播和针对 429 的 Retry-After。它的学习重点是“重试必须是有条件且有上限的”。

### 10.4 超时、取消与 deadline

推荐调用链在入口就定义总 deadline。例如用户请求最多允许 10 秒：

~~~text
入口还剩 10 秒
  -> 认证用 0.2 秒，剩 9.8 秒
  -> 检索用 1.5 秒，剩 8.3 秒
  -> 模型调用最多只能用剩余预算的一部分
  -> 不能每一层都各等 10 秒
~~~

若每一层都自己设置 10 秒超时，最坏延迟会层层叠加。应传播剩余时间，接近 deadline 时停止新尝试，并取消不再需要的后台工作。

### 10.5 幂等：把“重复请求”变成相同结果

幂等的含义是：同一个请求执行一次或多次，最终业务效果相同。HTTP 的 GET、PUT、DELETE 在语义上通常应幂等；POST 创建操作默认不一定幂等。

为创建类请求设置 Idempotency-Key：

~~~text
客户端：
POST /v1/document-jobs
Idempotency-Key: 8f87...

服务端：
- 第一次：将 key 与请求指纹、结果绑定，创建任务并返回 task_id。
- 相同 key 再来：直接返回原 task_id。
- 相同 key 但请求体不同：返回冲突，阻止误用。
~~~

数据库可以用唯一约束保护：

~~~sql
CREATE TABLE idempotency_record (
    idempotency_key TEXT PRIMARY KEY,
    request_hash TEXT NOT NULL,
    response_json JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
~~~

幂等键需要设置合理保存时间、按用户或租户隔离，并校验同 key 的请求内容一致。它不能用一个全局随机字符串替代业务语义。

### 10.6 熔断、限流和降级

当某个依赖持续失败时，仅靠重试会让它永远没有恢复机会。熔断器可粗略分为：

- Closed：正常调用；持续失败计数。
- Open：直接快速失败，不再请求故障依赖。
- Half-open：间隔后放少量探测请求；成功则恢复，失败则继续打开。

限流保护的是系统容量，例如限制每个租户的并发模型请求。降级保护的是用户体验，例如向量检索暂不可用时返回明确错误，或使用较小模型而不是无限等待。

熔断器不是一个必须立即引入的库。先有连接超时、错误分类、有限重试、指标和告警；当依赖级联故障确实出现时，再按现有框架实现或采用成熟组件。

## 11. 六个主题如何串成一个可靠流程

以“用户上传文档并等待知识库可检索”为例：

~~~text
1. 服务发现
   API 通过服务名调用文件服务、嵌入服务和向量库网关。

2. 负载均衡
   网关把上传请求分配给健康 API 实例；Worker 根据队列长度扩缩容。

3. 一致性
   API 在数据库事务中创建 document 与 task；任务状态变化有明确状态机。

4. 缓存一致性
   文档列表缓存失效或带版本；在索引完成前不把文档标为“可检索”。

5. 消息队列
   事务外盒发布 document_uploaded；Worker 异步解析、切块、嵌入。

6. 故障重试
   对临时模型网络错误有限重试；消息重复投递由 task_id 和消息 ID 幂等吸收。
~~~

任务状态可以设计得简单且可审计：

~~~text
PENDING -> PROCESSING -> INDEXED
                    \-> FAILED

重试时：
FAILED（可重试） -> PENDING
~~~

不要只保存一个模糊的 "status=error"。至少保存失败阶段、失败原因、尝试次数、最近一次尝试时间和 trace_id，才能让运维与用户知道下一步该做什么。

## 12. 初学者常见误区

| 误区 | 为什么不对 | 更好的做法 |
| --- | --- | --- |
| 把 IP 写死在代码里 | 扩缩容和故障迁移后即失效 | 用服务名和平台发现机制 |
| 多个 API 实例各自保存会话 | 请求换实例就丢状态 | 保持实例无状态，状态外置 |
| 超时就认定没有成功 | 对方可能已完成但响应丢失 | 写操作加幂等键和状态查询 |
| 任何异常都重试 | 会放大过载和业务错误 | 错误分类、次数上限、退避 |
| 消息 ack 后再执行业务 | Worker 崩溃会丢任务 | 业务成功后才确认 |
| 以为队列天然不重复 | 崩溃和重投递会带来重复 | 消费者幂等、唯一约束 |
| 直接相信缓存同步 | 删除缓存前可有旧读 | 明确陈旧窗口，关键读走真源 |
| 用分布式锁包住所有事情 | 锁会过期、阻塞、降低可用性 | 优先数据库原子操作与幂等 |
| 看到 200 就认为实例健康 | 可能尚未加载模型或依赖不可用 | 区分 liveness 与 readiness |
| 没有 trace_id | 跨服务日志无法关联 | 入口生成并向下游传播 |

## 13. 四周动手学习计划

### 第一周：单服务可靠性

- 用 FastAPI 写一个有 "/live"、"/ready" 和 trace_id 的服务。
- 用 httpx 调用一个故意会超时的接口，记录超时、重试次数和总耗时。
- 设计两个 POST 接口：一个没有幂等键，一个有幂等键；模拟客户端超时后重复提交。

验收问题：客户端收到超时时，服务端可能处于哪些状态？

### 第二周：Redis 缓存与状态外置

- 启动 Redis，实现 Cache-Aside 读取用户资料。
- 修改资料后先写 PostgreSQL，再删 Redis key。
- 为热 key 加短 TTL 和随机抖动，压测过期时的数据库请求数。
- 让两个 FastAPI 进程共用 Redis 会话，验证请求切换实例后状态仍存在。

验收问题：缓存删除失败时，用户会看到什么？系统靠什么最终恢复？

### 第三周：异步任务与幂等消费

- 用 Redis Streams、RabbitMQ 或 Celery 选择一个工具实现文档处理任务。
- 保存 task_id、状态、尝试次数和错误原因。
- 人为让 Worker 在业务写入后、确认消息前退出，观察重复投递。
- 给消费者加唯一约束，证明重复消息不会重复写入业务结果。

验收问题：系统为什么选择“至少一次 + 幂等”，而不简单追求“绝不重复”？

### 第四周：综合演练与可观测性

- 给 API、发布器、Worker 使用同一个 trace_id。
- 记录 P50/P95 延迟、错误率、队列积压和重试次数。
- 手动停止一个 Worker 或 Redis，观察系统是阻塞、降级、重试还是失败。
- 为每个故障写复盘：现象、影响、根因、检测信号、恢复动作、预防措施。

验收问题：如果队列积压增长，你先看哪些指标，如何判断应扩 Worker 还是降低生产速度？

## 14. 面试与工程表达模板

当被问到“如何设计可靠的 Python 服务”，可以按下面顺序回答：

1. 先定义业务正确性边界：哪些数据必须强一致，哪些允许最终一致。
2. API 实例保持无状态，使用服务发现与健康检查纳入负载均衡。
3. 对同步链路定义总超时、限流、错误分类、有限重试和降级。
4. 对异步任务用消息队列削峰；生产者用事务外盒避免丢事件。
5. 消费者按至少一次投递设计，用业务幂等键和数据库唯一约束抵抗重复。
6. 缓存以数据库为真实来源，采用 Cache-Aside，明确失效和陈旧窗口。
7. 用 trace_id、结构化日志、指标、告警和故障演练验证系统，而不是只描述组件名称。

这展示的是工程判断：你知道每项机制解决的故障模式、带来的代价，以及怎样验证它真的生效。

## 15. 一页速记

~~~text
服务发现：服务名 -> 健康实例地址。
负载均衡：健康实例中选择一个，算法要匹配真实负载。
一致性：先说清数据、副本、并发还是业务一致性。
缓存一致性：真实来源优先；常用“先写库，后删缓存”。
消息队列：异步削峰和解耦；默认按至少一次投递设计。
故障重试：仅重试暂时错误；退避、抖动、上限、deadline、幂等缺一不可。
~~~

最重要的学习方式不是背定义，而是每次设计都问四个问题：

1. 这一步失败或超时时，真实世界里可能已经发生了什么？
2. 请求、消息或回调重复到达时，结果会不会被重复执行？
3. 多个实例并发处理时，谁保存事实，谁只是副本？
4. 我用什么日志、指标、测试或故障演练证明答案？

能持续回答这四个问题，你就已经开始用分布式系统工程师的方式思考了。
