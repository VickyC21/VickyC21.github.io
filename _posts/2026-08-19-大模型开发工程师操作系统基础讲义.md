# 大模型开发工程师的操作系统基础：进程、线程、协程、内存、文件描述符与 CPU/GPU 资源竞争

> 适合对象：刚开始从事或准备从事大模型开发的 Python 初学者。
>
> 学习目标：不只记住术语，而是能回答三个工程问题：**任务在哪里运行、它占用了什么资源、资源不足或竞争时会发生什么。**

大模型开发不只是“向模型发一个 HTTP 请求”。一个真实请求可能同时涉及：Web 服务进程、处理请求的线程或协程、网络连接占用的文件描述符、提示词和响应占用的内存、CPU 上的数据预处理，以及 GPU 上的推理任务和显存。理解这些资源的边界，是排查超时、卡顿、OOM、吞吐低和服务崩溃的基础。

本文以 Python 3.11+ 为例。大多数示例只用标准库，可以复制为 `.py` 文件运行；PyTorch 示例会明确标注为可选。

## 1. 先建立总模型：程序、执行单元和资源

先区分四个容易混淆的词：

| 名词 | 直观含义 | 操作系统视角 | 你在 LLM 服务中看到的例子 |
| --- | --- | --- | --- |
| 程序 | 静态代码和依赖 | 磁盘上的可执行文件、脚本或包 | `uvicorn`、Python 脚本、模型推理程序 |
| 进程 | 一次运行中的程序实例 | 独立的虚拟地址空间和资源容器 | 一个 Web worker、一个训练进程 |
| 线程 | 进程内部实际被调度执行的路径 | 共享进程资源的执行单元 | 处理同步 SDK 调用的工作线程 |
| 协程 | 应用层主动让出执行权的任务 | 通常由一个线程中的事件循环调度 | 同时等待多个模型 API 响应 |

可以把进程想成一间独立办公室：它有自己的资料柜（内存）、门牌号（PID）和已打开的门/电话线路（文件描述符）。线程是办公室内的工作人员：共享资料柜，但每个人有自己的工作台。协程更像一个工作人员管理的待办事项清单：当一件事需要等待外部回复时，工作人员会先处理另一件事。

### 1.1 大模型请求的资源路径

以“用户向 RAG 问答服务提问”为例：

1. 操作系统将网络请求交给 Web 服务进程。
2. 事件循环中的协程等待向量库、重排器和模型服务的 I/O 响应。
3. 线程或子进程可能执行阻塞 SDK、文档解析或 CPU 密集型文本清洗。
4. 请求体、检索结果、Prompt、流式 token 暂存于 RAM。
5. HTTP 连接、日志文件、数据库连接、管道都各占用文件描述符。
6. 本地模型服务把 token 张量送至 GPU，使用显存和 GPU 计算时间。

下面的章节一直围绕这条路径。每学习一个概念，都问自己：**它共享什么、隔离什么、等待什么、谁负责释放资源。**

## 2. 并发和并行：先判断问题类型

**并发（concurrency）**是多个任务在同一段时间内都有进展。单核 CPU 也能并发：任务 A 等网络时，系统去运行任务 B。

**并行（parallelism）**是在同一时刻真的有多个执行单元运行，例如多个 CPU 核执行不同进程，或 GPU 的大量核心同时执行计算。

它们不是同义词：

- 100 个协程等待 HTTP 响应，可以有很高并发，但通常只消耗一个 Python 线程，并不意味着 100 路 CPU 并行计算。
- 4 个进程在 4 个 CPU 核上做文本分词，才可能获得 CPU 并行。
- 把 CPU 密集循环塞进 1,000 个协程，不会让计算更快，反而增加调度和内存开销。

### 2.1 I/O 密集和 CPU 密集

先给任务分类，再选择进程、线程或协程：

| 类型 | 时间主要花在哪里 | 常见例子 | 常见选择 |
| --- | --- | --- | --- |
| I/O 密集 | 网络、磁盘、数据库、远程模型响应 | 调用模型 API、读对象存储、访问 Redis | 协程；或线程池包装阻塞库 |
| CPU 密集 | Python 或原生代码计算 | OCR 后清洗、压缩、复杂解析、特征计算 | 进程池；或会释放 GIL 的原生库 |
| GPU 密集 | GPU kernel 执行 | 本地模型预填充、生成、训练 | 控制请求并发和批处理，不盲目加 Python 并发 |
| 混合型 | 上述阶段交替出现 | RAG、批量文档入库 | 分阶段处理，每段用合适的执行模型 |

一个简单准则：如果任务大部分时间在“等”，优先考虑提高并发；如果任务大部分时间在“算”，优先考虑使用更多真正的计算资源，或减少计算量。

## 3. 进程：资源隔离的基本单位

进程是操作系统分配和隔离资源的基本单位。每个进程至少有：

- PID（进程标识）；
- 独立的虚拟地址空间；
- 自己的文件描述符表；
- 一个或多个线程；
- 环境变量、当前工作目录、权限和退出状态；
- 由内核维护的调度、内存映射和打开资源信息。

### 3.1 为什么进程默认不共享变量

两个 Python 进程即使运行同一份代码，普通变量也不共享。这样可以避免一个进程随意破坏另一个进程的数据，但代价是进程间通信（IPC）需要显式设计。

```python
# process_isolation.py
from multiprocessing import Process
import os

counter = 0


def add_one() -> None:
    global counter
    counter += 1
    print(f"子进程 PID={os.getpid()}，counter={counter}")


if __name__ == "__main__":
    print(f"父进程 PID={os.getpid()}，counter={counter}")
    process = Process(target=add_one)
    process.start()
    process.join()
    print(f"父进程等待结束后，counter={counter}")
```

预期现象：子进程中 `counter` 变为 `1`，父进程中的 `counter` 仍是 `0`。这不是同步失败，而是隔离设计。

> Windows 默认采用 `spawn` 启动子进程，会重新导入模块；因此创建进程的代码必须放在 `if __name__ == "__main__":` 之下。否则可能递归创建子进程。

### 3.2 进程生命周期

常见状态可以粗略理解为：创建 -> 就绪 -> 运行 -> 等待 -> 结束。等待可能来自 I/O、锁、子进程或定时器。父进程需要负责回收子进程：在 Python 中通常调用 `join()`。

若一个子进程结束而父进程没有回收其退出状态，在 Unix 系统中可能形成僵尸进程。生产服务通常由进程管理器、容器编排系统或 Web 服务器管理 worker 生命周期，但你仍要知道：**子进程不是“启动后就不用管”的后台魔法。**

### 3.3 进程间通信（IPC）

常见方式及取舍：

| 方式 | 适合什么 | 代价或注意点 |
| --- | --- | --- |
| `multiprocessing.Queue` | 进程池任务和结果 | 数据通常需要序列化；队列也要有容量边界 |
| `Pipe` | 少量、一对一通信 | 连接端的关闭要清晰 |
| 共享内存 | 大块数组、图像、张量元数据 | 生命周期和并发访问更复杂 |
| Socket / HTTP / gRPC | 独立服务之间 | 网络协议、超时、认证和重试不可省略 |
| 数据库、Redis、消息队列 | 跨机器、可持久化工作流 | 要定义幂等、可见性、失败恢复 |

示例：主进程通过 `Queue` 收结果。

```python
from multiprocessing import Process, Queue


def square(number: int, result_queue: Queue) -> None:
    result_queue.put((number, number * number))


if __name__ == "__main__":
    result_queue = Queue()
    workers = [
        Process(target=square, args=(number, result_queue))
        for number in range(4)
    ]
    for worker in workers:
        worker.start()

    results = [result_queue.get() for _ in workers]
    for worker in workers:
        worker.join()

    print(sorted(results))
```

### 3.4 什么时候用进程池

Python 的 CPython 实现有 GIL，纯 Python CPU 计算无法靠多个线程稳定地在多个核上并行。此时可使用 `ProcessPoolExecutor`：

```python
from concurrent.futures import ProcessPoolExecutor


def count_primes(limit: int) -> int:
    count = 0
    for number in range(2, limit):
        for divisor in range(2, int(number**0.5) + 1):
            if number % divisor == 0:
                break
        else:
            count += 1
    return count


if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=2) as executor:
        results = list(executor.map(count_primes, [50_000, 55_000]))
    print(results)
```

不要把 `max_workers` 直接设成很大的数。每个进程有启动、内存和序列化成本；若每个子进程还加载一个大模型，显存或 RAM 会迅速耗尽。进程数量必须由机器容量、任务特征和压测结果决定。

## 4. 线程：共享内存的执行单元

同一进程的线程共享堆内存、全局变量、打开的文件和 socket，因此通信简单，也因此容易产生竞态条件。

每个线程仍有自己的调用栈和局部变量。一个线程函数里的局部变量通常不直接被其他线程看见；但它指向的全局对象、传入的可变对象和类变量可能被共享。

### 4.1 GIL 到底限制了什么

CPython 的全局解释器锁（GIL）使得同一时刻通常只有一个线程执行 Python 字节码。因此：

- 多线程很适合处理网络、磁盘、数据库等阻塞 I/O；等待 I/O 时其他线程可运行。
- 多线程通常不能让纯 Python 的 CPU 大循环线性加速。
- NumPy、PyTorch、压缩库等可能在原生代码中释放 GIL；是否能并行应以该库文档和实际测量为准。
- GIL **不等于线程安全**。业务读-改-写过程仍可能被交错执行。

### 4.2 竞态条件：看似简单的余额扣减

下面的代码故意在“读取余额”和“写回余额”之间暂停。两个线程都会看见余额足够，最终可能多扣一次。

```python
from threading import Lock, Thread
import time


class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance
        self.lock = Lock()

    def withdraw_without_lock(self, amount: int) -> bool:
        if self.balance < amount:
            return False
        time.sleep(0.01)  # 模拟数据库或外部调用导致的切换窗口
        self.balance -= amount
        return True

    def withdraw_with_lock(self, amount: int) -> bool:
        with self.lock:
            if self.balance < amount:
                return False
            time.sleep(0.01)
            self.balance -= amount
            return True


def try_withdraw(account: Account, safe: bool) -> None:
    method = account.withdraw_with_lock if safe else account.withdraw_without_lock
    print(method(80))


for safe in (False, True):
    account = Account(balance=100)
    threads = [Thread(target=try_withdraw, args=(account, safe)) for _ in range(2)]
    for thread in threads:
        thread.start()
    for thread in threads:
        thread.join()
    print(f"safe={safe}, final balance={account.balance}")
```

无锁版本可能得到 `-60`。加锁后，只有一个线程能完成扣款。真实支付系统还必须使用数据库事务、幂等键等更强约束；线程锁只保护单个进程内的临界区，不能保护多进程或多机器。

### 4.3 常用同步工具

| 工具 | 解决的问题 | LLM 服务中的例子 |
| --- | --- | --- |
| `Lock` | 同一时刻只允许一个线程修改临界资源 | 更新内存缓存中的共享统计值 |
| `RLock` | 同一线程可重入 | 嵌套调用同一把锁的少数场景 |
| `Semaphore` | 限制同时使用的数量 | 最多 8 个同步模型请求 |
| `Event` | 通知“可以开始/应停止” | 优雅关闭后台线程 |
| `Queue` | 安全传递任务并提供缓冲 | 日志、文档解析任务、批处理 |
| `Condition` | 等待某个复杂条件 | 低层并发协调，通常优先考虑队列 |

锁的原则：临界区尽量短；不要在持锁期间执行慢网络调用；多把锁必须有固定获取顺序，否则可能死锁。

### 4.4 用线程包装阻塞 I/O

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time


def blocking_model_sdk(prompt: str) -> str:
    time.sleep(0.5)  # 模拟没有异步接口的 SDK
    return f"回答：{prompt}"


prompts = ["问题 A", "问题 B", "问题 C"]
with ThreadPoolExecutor(max_workers=3) as executor:
    futures = [executor.submit(blocking_model_sdk, prompt) for prompt in prompts]
    for future in as_completed(futures):
        print(future.result())
```

线程池的 `max_workers` 是资源治理的一部分：太小会排队，太大可能触发远端限流、占满连接池、增加内存和上下文切换。它不是越大越好。

## 5. 协程与 asyncio：高并发等待的工具

协程是能在 `await` 处主动挂起、稍后恢复的函数。`async def` 只是定义协程函数；调用它得到的是协程对象，只有 `await`、`create_task()` 或任务组调度后才会真正执行。

### 5.1 事件循环如何工作

一个 `asyncio` 事件循环通常运行在一个线程里。它维护很多任务：当任务 A `await` 网络 I/O 时，事件循环运行任务 B；当 A 的 I/O 完成时，事件循环再恢复 A。

这意味着：协程擅长在**可等待的 I/O**之间切换。若协程里直接执行很久的 CPU 循环或 `time.sleep()`，事件循环无法切换，所有请求都会被拖住。

```python
import asyncio
import time


async def wrong() -> None:
    time.sleep(1)  # 阻塞整个事件循环


async def right() -> None:
    await asyncio.sleep(1)  # 让出控制权，其他任务可继续
```

### 5.2 并发等待多个独立任务

```python
import asyncio
import time


async def fetch(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{name} 完成"


async def main() -> None:
    started_at = time.perf_counter()
    results = await asyncio.gather(
        fetch("向量检索", 0.4),
        fetch("用户画像", 0.2),
        fetch("权限检查", 0.3),
    )
    print(results)
    print(f"耗时：{time.perf_counter() - started_at:.2f} 秒")


asyncio.run(main())
```

总耗时接近最长的 `0.4` 秒，而非三者相加。前提是任务彼此独立，且内部确实使用异步 I/O。

### 5.3 结构化并发、超时和取消

Python 3.11 的 `TaskGroup` 能把同一业务请求的子任务绑定在一起：离开任务组前会等待任务结束；一个任务发生未处理异常时，其他任务会被取消。这比“随手 `create_task()` 后忘记回收”安全得多。

```python
import asyncio


async def query_source(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{name} 的结果"


async def collect_context() -> list[str]:
    try:
        async with asyncio.timeout(1):
            async with asyncio.TaskGroup() as group:
                policy = group.create_task(query_source("知识库", 0.3))
                profile = group.create_task(query_source("用户资料", 0.2))
        return [policy.result(), profile.result()]
    except TimeoutError:
        return ["检索超时，使用降级回答"]


print(asyncio.run(collect_context()))
```

取消是正常控制流：例如浏览器客户端断开、请求达到整体超时、服务正在关闭。任何持有连接、文件、锁的协程都应在 `finally` 中释放资源。

```python
import asyncio


async def stream_answer() -> None:
    try:
        while True:
            await asyncio.sleep(0.2)
            print("生成一个 token")
    finally:
        print("关闭下游流、归还连接、记录取消原因")
```

### 5.4 给异步服务设置背压

不能对一万个请求都立即 `create_task()`，因为任务对象、连接、内存和远端配额都有限。信号量限制“同时执行数”，有界队列限制“排队长度”，二者共同形成背压。

```python
import asyncio


async def call_model(item: int, limiter: asyncio.Semaphore) -> str:
    async with limiter:
        await asyncio.sleep(0.2)
        return f"item={item}"


async def main() -> None:
    limiter = asyncio.Semaphore(4)
    results = await asyncio.gather(
        *(call_model(item, limiter) for item in range(12)),
    )
    print(results)


asyncio.run(main())
```

生产中还要定义队列满时的策略：等待多久、拒绝还是降级、是否按租户隔离、是否允许重试。没有边界的并发，本质上是把故障推迟到内存耗尽或下游雪崩时才暴露。

## 6. 进程、线程、协程如何选择

| 情况 | 优先方案 | 原因 | 不应做什么 |
| --- | --- | --- | --- |
| 同时请求多个异步 HTTP 服务 | `asyncio` | 主要在等待网络 | 在事件循环里用阻塞客户端 |
| SDK 只有同步 API，且主要等待网络 | 线程池或 `asyncio.to_thread()` | 不阻塞事件循环 | 为每个请求新建无限线程 |
| 纯 Python 的 CPU 密集任务 | 进程池 | 绕过 CPython GIL | 用很多协程硬跑计算 |
| NumPy/PyTorch 等原生计算 | 先测量；遵守库的线程设置 | 可能释放 GIL，且内部已并行 | 外层再套大量线程造成过度订阅 |
| 本地 GPU 推理 | 单/少数推理服务进程 + 有界请求队列 | GPU、显存和批处理是瓶颈 | 每个 API 请求都加载模型 |
| 多个机器间的任务 | 队列或服务协议 | 进程边界已经跨机器 | 依赖进程内锁或全局变量 |

## 7. 内存：从虚拟地址到 Python 对象和模型显存

内存问题常被统称为“内存不够”，但至少要区分 RAM、虚拟内存、文件页缓存和 GPU 显存。

### 7.1 虚拟内存不是“假的内存”

每个进程看到的是自己的**虚拟地址空间**。操作系统通过页表把虚拟地址映射到物理 RAM 页，必要时也可能映射到磁盘上的交换空间或内存映射文件。

好处是隔离：进程 A 的地址 `0x...` 不能直接读写进程 B 的同名地址。代价是地址翻译、缺页处理和内存管理。

常见区域：

- **代码段**：机器指令，通常可共享只读页。
- **堆（heap）**：动态创建的对象，Python 对象主要在这里。
- **栈（stack）**：函数调用帧和局部引用；每个线程通常有自己的栈。
- **内存映射区域**：共享库、映射文件、某些大对象分配。
- **页缓存（page cache）**：内核缓存文件数据，加速重复读写；它也会占用可回收 RAM。

### 7.2 RSS、共享页和“看起来内存很高”

排查进程内存时常见指标：

- **RSS**：该进程当前驻留在物理 RAM 中的页，可能包含共享页。
- **VMS/虚拟内存大小**：进程可见的虚拟地址范围，不等于实际 RAM 占用。
- **PSS**：共享页按进程数量分摊后的估计，常更适合比较多个 worker。

因此，多个 worker 都加载相同的共享库时，不能简单把每个 RSS 相加就认定为真实占用。反过来，进程一旦在写时复制（copy-on-write）后修改了原本共享的页，真实内存会增长。

### 7.3 Python 内存管理与泄漏

CPython 主要使用引用计数：对象引用数归零时，通常立即释放；循环引用由垃圾回收器额外处理。但“Python 对象不可达”不等于操作系统立刻看到 RSS 降低，因为 Python 内存分配器可能保留内存块供后续复用。

真正高频的泄漏来源常是：

- 全局 `list`/`dict` 持续累积请求、Prompt 或响应；
- 缓存没有大小、过期或淘汰策略；
- 闭包、回调、后台任务意外持有大对象；
- 未关闭的文件、socket、数据库游标；
- 每次请求都创建昂贵客户端或加载模型；
- 把所有流式 token 拼成巨大字符串后再保留多份副本。

可用 `tracemalloc` 找到 Python 分配热点：

```python
import tracemalloc

tracemalloc.start()

cache = []
for number in range(10_000):
    cache.append("x" * 1_000)

current, peak = tracemalloc.get_traced_memory()
print(f"当前追踪内存：{current / 1024 / 1024:.2f} MiB")
print(f"峰值追踪内存：{peak / 1024 / 1024:.2f} MiB")

snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:3]:
    print(stat)
```

它追踪的是 Python 分配，无法完整解释 NumPy、PyTorch、C 扩展或内核页缓存的内存，因此要把它和系统监控结合使用。

### 7.4 OOM、交换和内存压力

当可用 RAM 不足时，系统可能回收页缓存、将不活跃页换出到磁盘，或终止进程。交换（swap）不是免费内存：磁盘比 RAM 慢得多，频繁换页会造成抖动，表现为服务整体非常慢。

处理顺序应是：

1. 先确认增长的是哪个进程、哪类内存；
2. 查是否存在无边界队列、缓存或并发；
3. 减少数据副本、缩小批次和上下文；
4. 给请求、队列、缓存和 worker 数量设上限；
5. 只有确认容量确实不足后，再扩容或调整部署。

重启进程可以暂时恢复，但不能解释泄漏来源，也不能替代边界控制。

### 7.5 LLM 中的 RAM 与显存

本地模型推理的显存主要来自：

| 组成 | 含义 | 为什么会增长 |
| --- | --- | --- |
| 模型权重 | 参数加载到 GPU 后的常驻数据 | 模型更大、精度更高 |
| KV Cache | 保存已处理 token 的注意力键和值 | 上下文更长、并发请求更多 |
| 激活值/临时张量 | 每层计算中间结果 | 批次更大、训练时更明显 |
| 框架缓存/碎片 | 分配器为复用保留的块 | 频繁不同尺寸分配可能碎片化 |

一个重要结论：**长上下文和高并发会共同放大 KV Cache。** 即使模型权重不变，服务也可能在流量高峰发生 GPU OOM。

## 8. 文件描述符：一切打开资源的编号

在 Unix/POSIX 体系中，文件描述符（FD）是进程内一个小整数，用来引用内核管理的打开资源。名字里有“文件”，但它还包括：

- 普通文件和日志文件；
- TCP/Unix socket；
- 管道；
- 标准输入、标准输出、标准错误；
- 某些设备、事件通知对象。

通常 `0`、`1`、`2` 分别代表标准输入、标准输出、标准错误。Python 的文件对象和 socket 对象在底层都对应打开资源；不要依赖编号的具体值，而要理解它们都需要关闭。

### 8.1 为什么 FD 泄漏会让服务“突然不能连网”

操作系统会限制单个进程能打开的 FD 数。若每个请求都新建 HTTP 连接、打开文件或数据库游标却不关闭，FD 持续上涨，最终可能报 `Too many open files`。此时错误可能出现在完全无关的地方：打开日志失败、接受新连接失败或 DNS 查询失败。

正确的资源所有权写法：

```python
from pathlib import Path

path = Path("answer.txt")
with path.open("w", encoding="utf-8") as file:
    file.write("模型回答")
# 离开 with 后，无论是否抛异常，文件都会关闭。
```

网络客户端也应遵守自己的上下文管理器或 `close()` 约定。长期复用的 HTTP/数据库客户端应在应用生命周期创建和关闭，而不是在每个请求里任意创建，也不是永远不释放。

### 8.2 文件描述符的两层关系

可以简化为：进程的 FD 表 -> 内核的打开文件对象 -> 实际文件/socket。两个 FD 可能指向同一个内核对象，例如父子进程继承资源或显式复制描述符时。关闭一个引用不一定关闭底层资源，只有最后一个引用释放时才会彻底关闭。

这也是子进程管理中的坑：子进程意外继承管道写端，会让父进程一直等不到 EOF。创建子进程时应明确哪些句柄需要继承，哪些不应继承。

### 8.3 如何观察 FD

- Linux：`lsof -p <PID>` 可查看某进程打开资源；`/proc/<PID>/fd` 目录也可检查。
- macOS：可使用 `lsof -p <PID>`。
- Windows：使用资源监视器、Process Explorer 等系统工具检查句柄；概念上对应“handle”，不完全等同于 Unix FD。

以下 Python 示例只在 Linux 上有意义：

```python
from pathlib import Path
import os

pid = os.getpid()
fd_dir = Path(f"/proc/{pid}/fd")
if fd_dir.exists():
    print(f"当前打开 FD 数：{len(list(fd_dir.iterdir()))}")
else:
    print("当前系统未提供 /proc/<PID>/fd，请用系统工具查看句柄。")
```

## 9. CPU 资源竞争：调度、上下文切换和过度订阅

CPU 核只能在某一瞬间运行有限数量的线程。操作系统调度器在可运行线程之间分配时间片。当可运行线程数量远大于 CPU 核数时，会发生更多上下文切换：保存一个线程的寄存器和状态，再恢复另一个线程。

上下文切换本身不是错误，但过多切换会消耗时间、破坏 CPU 缓存局部性，并拉高延迟。

### 9.1 过度订阅（oversubscription）

假设机器有 8 个 CPU 核：

- Web 服务启动 8 个 worker；
- 每个 worker 的线程池又允许 32 个线程；
- PyTorch/BLAS 在每个 worker 内再使用多线程；
- 同时还有索引、日志和监控任务。

这不是“8 核就能处理很多任务”的简单加法，而是多个调度器同时争抢同一批核。现象可能是 CPU 利用率很高但吞吐没有提升、P99 延迟恶化，甚至远程请求超时。

排查 CPU 竞争时要同时看：CPU 利用率、可运行队列、上下文切换、线程数、每个库的内部线程数、请求排队时间和端到端延迟。

### 9.2 CPU 密集任务的基准方法

不要只比较“代码是否跑完”，要用 `time.perf_counter()` 测量同样输入、同样机器、预热后的耗时，并至少比较：单任务、合理并发、过高并发。

```python
import os
import time


def cpu_work(size: int) -> int:
    total = 0
    for number in range(size):
        total += number * number
    return total


print(f"逻辑 CPU 数：{os.cpu_count()}")
started_at = time.perf_counter()
print(cpu_work(5_000_000))
print(f"耗时：{time.perf_counter() - started_at:.3f} 秒")
```

单次数字不能直接外推到生产。缓存、输入长度、其他负载、功耗限制和 Python 版本都会影响结果。

## 10. GPU 资源竞争：显存、计算流和推理调度

GPU 不是“CPU 更快的替代品”。在 LLM 服务中，CPU 主要处理网络、tokenizer、请求调度和数据准备；GPU 主要执行矩阵计算。GPU 的关键瓶颈往往是显存容量、显存带宽、批处理策略和 kernel 调度。

### 10.1 GPU 为什么会排队

多个进程或请求都可能争用同一块 GPU：

- 各自加载模型权重，重复占用显存；
- 同时分配 KV Cache，触发 OOM；
- 各自提交 kernel，造成计算排队；
- 训练任务与在线推理混跑，导致延迟不稳定；
- 小请求很多，GPU 利用率低但调度开销高；
- 长 Prompt 的 prefill 占用较久，短请求被拖慢。

因此，推理服务通常需要有界并发、请求队列、连续批处理、长度限制和公平调度。最重要的不是“让每个请求马上进入 GPU”，而是让总吞吐、尾延迟和稳定性符合目标。

### 10.2 PyTorch 显存观察（可选）

下面示例需要安装 PyTorch 和可用 CUDA。`memory_allocated()` 是当前张量实际占用的估计，`memory_reserved()` 是框架缓存分配器保留的显存，二者不同并不必然是泄漏。

```python
import torch

if not torch.cuda.is_available():
    raise SystemExit("未检测到可用 CUDA GPU")

print(torch.cuda.get_device_name(0))
print(f"已分配：{torch.cuda.memory_allocated() / 1024**2:.1f} MiB")
print(f"已保留：{torch.cuda.memory_reserved() / 1024**2:.1f} MiB")

with torch.inference_mode():
    tensor = torch.randn(2_048, 2_048, device="cuda")
    result = tensor @ tensor
    torch.cuda.synchronize()  # 仅用于准确测量；会阻塞 CPU

print(f"峰值已分配：{torch.cuda.max_memory_allocated() / 1024**2:.1f} MiB")
```

性能测量时要注意 CUDA 默认异步：CPU 提交计算后可能立刻返回，所以不加 `torch.cuda.synchronize()` 的计时常常偏小。线上路径不要为了“准确计时”到处同步，因为同步会牺牲并发；应由监控系统在合适位置收集指标。

### 10.3 GPU OOM 的正确排查顺序

1. 确认发生 OOM 的 GPU、进程、模型、请求长度和并发量。
2. 区分权重常驻、KV Cache 增长、训练激活值、临时张量和内存碎片。
3. 先降低一个可解释的变量：并发、最大上下文、最大生成长度或 batch size。
4. 检查是否有重复模型实例或未结束的旧进程。
5. 再考虑量化、更大显存 GPU、模型拆分或专业推理框架。

`torch.cuda.empty_cache()` 只能释放未被活跃张量使用的缓存，不能解决仍被引用的大张量、无边界 KV Cache 或容量规划错误。

## 11. 资源竞争的统一解法：边界、排队、取消和观测

CPU、GPU、内存、FD 和下游 API 的竞争看似不同，解决思路却很接近：

| 问题 | 必要边界 | 观测信号 | 常见治理措施 |
| --- | --- | --- | --- |
| CPU | worker/线程数 | CPU、上下文切换、P95 | 限制池大小，进程隔离，测量后调参 |
| 内存 | 队列、缓存、请求体大小 | RSS、堆快照、OOM | 有界队列、淘汰策略、流式处理 |
| FD/连接 | 连接池、打开数 | FD 数、连接错误 | 复用客户端、`with`、超时关闭 |
| 远端模型 API | 并发和速率 | 429、排队时间、错误率 | semaphore、限流、退避、降级 |
| GPU | batch、上下文、并发 | 显存、利用率、TTFT | 调度队列、连续批处理、长度限制 |

### 11.1 一个带资源边界的异步调用骨架

```python
import asyncio

MODEL_CONCURRENCY = 8
model_limiter = asyncio.Semaphore(MODEL_CONCURRENCY)


async def call_remote_model(prompt: str) -> str:
    # 这里应替换为真正支持 async 的 HTTP/SDK 调用。
    await asyncio.sleep(0.2)
    return f"回答：{prompt[:20]}"


async def answer(prompt: str) -> str:
    if len(prompt) > 8_000:
        raise ValueError("输入过长，请先截断或分块")

    try:
        async with asyncio.timeout(10):
            async with model_limiter:
                return await call_remote_model(prompt)
    except TimeoutError as error:
        raise RuntimeError("模型调用超时，已停止等待") from error
```

这个骨架没有假装解决所有问题，但它明确了输入边界、超时边界和并发边界。生产系统还需要按用户/租户限流、重试策略、取消传播、日志和指标。

## 12. 从现象到定位：常见故障清单

### 12.1 “async 接口并发很低”

检查：是否在 `async def` 内用了 `requests`、`time.sleep()`、同步数据库驱动、同步文件解析或大 CPU 循环。它们会阻塞事件循环。

修复方向：使用异步库，或将确定会阻塞的同步 I/O 放到受控线程池；CPU 密集任务放进受控进程池。

### 12.2 “CPU 100%，请求却越来越慢”

检查：任务是否 CPU 密集；worker、线程池和底层数学库是否过度订阅；是否存在忙等循环；是否把大 JSON 反复序列化。

修复方向：先做 profile，再减少并发/线程数或转进程池；避免把大计算放在事件循环。

### 12.3 “内存持续上涨，重启后短暂恢复”

检查：无界缓存、无界队列、积压任务、保存完整上下文、未完成后台任务、每请求创建客户端、重复加载模型。

修复方向：为每个集合建立容量和生命周期，使用 heap snapshot 或 `tracemalloc` 定位持有者，复现增长曲线后再改。

### 12.4 “Too many open files”

检查：是否未关闭文件/socket/响应对象/数据库游标；连接池是否失控；是否有子进程继承句柄。

修复方向：使用上下文管理器，复用并正确关闭客户端，限制并发连接，观察 FD 数是否随请求完成回落。

### 12.5 “GPU 利用率低但响应慢”

检查：请求是否太小且频繁；tokenization 或网络是否是瓶颈；GPU 是否等待 CPU；是否没有批处理；是否被其他进程占用。

修复方向：分解 TTFT、prefill、decode 和网络时间，按场景调整批处理和并发，而不是仅盯一个 GPU 利用率数字。

## 13. 建议的学习实验

按顺序完成以下实验，每个实验都记录“输入、观察、结论”：

1. 运行进程隔离示例，修改父/子进程变量，观察为什么不共享。
2. 运行余额竞态示例，确认无锁版本出现错误；再说明锁保护的范围。
3. 把 `asyncio.sleep()` 换为 `time.sleep()`，观察并发任务总耗时的变化。
4. 给异步模型模拟器加入信号量，分别设为 1、4、16，记录吞吐、排队和平均延迟。
5. 用 `tracemalloc` 创建并清理一个缓存，比较当前内存和峰值。
6. 在 Linux 或系统工具中观察一个脚本打开文件前后的 FD/句柄数量。
7. 若有 CUDA，在固定输入下比较不同 batch size 的显存峰值和延迟；一次只改变一个变量。

### 13.1 最小项目练习：有边界的批量摘要器

目标：读取一个目录中的文本文件，调用模型生成摘要，并限制资源使用。

验收标准：

- 文件读取使用 `with`，不会泄漏文件句柄；
- 同时最多处理 N 个任务；
- 每个模型调用有超时；
- 队列有最大长度；
- 取消时能停止后续工作并释放资源；
- 记录每个文件的耗时、错误类型和输入长度；
- 人为制造一个慢任务、一个异常文件、一个过长文件，验证失败路径。

这个练习比简单的“并发调用 100 次 API”更接近生产工程，因为它要求你给每一种资源和失败模式设边界。

## 14. 面试与实战速记

- **进程**：隔离内存和资源，适合 CPU 并行与故障隔离；通信有成本。
- **线程**：共享内存，适合阻塞 I/O；需要同步；CPython GIL 限制纯 Python CPU 并行。
- **协程**：单线程中高效等待 I/O；只能在 `await` 处切换；阻塞代码会拖住事件循环。
- **内存**：先分清 Python 堆、RSS、页缓存和显存；所有缓存、队列、上下文和并发都应有上限。
- **文件描述符**：文件、socket、管道等打开资源的引用；必须关闭，泄漏会导致服务无法建立新连接。
- **CPU 竞争**：线程/进程/内部库太多会过度订阅；用基准和 profile 决定池大小。
- **GPU 竞争**：重点看显存、KV Cache、批处理、请求长度和排队；更多 Python 并发不等于更高 GPU 吞吐。
- **资源治理**：限流、信号量、有界队列、超时、取消、上下文管理器和指标，缺一项都可能让小故障扩大。
