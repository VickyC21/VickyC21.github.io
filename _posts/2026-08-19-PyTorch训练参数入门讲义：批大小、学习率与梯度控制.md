# PyTorch 训练参数入门讲义：批大小、学习率与梯度控制

本文面向刚开始学习大模型训练的开发者。目标不是记住几个 API，而是建立可排错的训练模型：当训练变慢、发散、出现 NaN 或显存不足时，知道优先检查什么、为什么调，以及改动会带来什么代价。

本文解释五个训练控制项：batch size（批大小）、学习率、梯度裁剪、梯度累积和混合精度训练。示例基于 PyTorch 2.x；GPU 相关示例在 CUDA 环境中效果最明显。

## 1. 训练循环中的位置

一次最小训练迭代如下：

    model.train()

    for features, targets in train_loader:
        optimizer.zero_grad()
        predictions = model(features)
        loss = criterion(predictions, targets)
        loss.backward()
        optimizer.step()

把模型参数想成一组旋钮，损失函数是一块有高低的地形：

- 前向传播：测量当前位置的损失。
- 反向传播：计算每个旋钮向哪个方向转会使损失下降，即梯度。
- 优化器更新：按某个步长沿下降方向移动。
- 重复很多次：希望在训练集和未见数据上都得到较低损失。

| 机制 | 控制对象 | 解决的问题 | 主要代价 |
| --- | --- | --- | --- |
| batch size | 一次计算多少样本 | 梯度稳定性与吞吐 | 显存增加 |
| 学习率 | 单次更新走多远 | 收敛速度与稳定性 | 过大易发散，过小很慢 |
| 梯度裁剪 | 允许梯度最大多大 | 防止极端更新破坏训练 | 过低会抑制学习 |
| 梯度累积 | 几个小批次后更新 | 显存不足时模拟大 batch | 增加迭代开销 |
| 混合精度 | 计算使用的数值精度 | 节省显存、提高吞吐 | 需处理数值稳定性 |

它们会互相影响。尤其要记住：

    有效批大小 = 每卡 batch size × 梯度累积步数 × GPU 数量

有效批大小变化后，学习率、学习率调度器和训练总步数都要重新检查。

## 2. 样本、批次、迭代、更新与 epoch

假设训练集有 10,000 条样本，batch_size=100：

- 样本：一条训练数据，例如一张图或一段“指令-回答”文本。
- 批次：一次送入模型的一组样本，此处为 100 条。
- 迭代：处理一个批次并完成前向、反向计算。
- 更新：调用一次 optimizer.step()。
- epoch：完整遍历训练集一次。没有梯度累积时，此例每个 epoch 有 100 次迭代和约 100 次更新。

若 batch_size=25、gradient_accumulation_steps=4，则连续处理 4 个微批次再更新。一个 epoch 仍有 400 次迭代，但只有约 100 次参数更新；有效批大小仍是 100。

不要混淆“微批次迭代数”与“参数更新数”。max_steps、学习率预热和 scheduler.step() 通常应按更新次数计算。

## 3. Batch Size：一次让模型看多少数据

### 3.1 为什么需要 batch

理论上，全量梯度是所有训练样本梯度的平均值；但训练集很大，显存无法容纳全部中间结果。实际做法是随机取一个小批次，以其平均梯度近似全量梯度：

    g_batch = (1 / B) × Σ grad(loss_i)
    θ_new = θ_old - learning_rate × g_batch

其中 B 是批大小，θ 是模型参数。常见损失函数默认 reduction="mean"，即在批次内求平均。

假设某个参数在四条样本上的梯度是 [2, -1, 3, 0]：

- batch_size=1 时，一步看到的梯度可能是 2、-1、3 或 0，方向很抖。
- batch_size=4 时，平均梯度是 1，方向通常更稳定。

### 3.2 小 batch 与大 batch 的取舍

| 特性 | 小 batch | 大 batch |
| --- | --- | --- |
| 梯度估计 | 噪声较大 | 更接近全量梯度 |
| 单步显存 | 较低 | 较高 |
| GPU 利用率 | 可能吃不满 | 往往更高 |
| 每个 epoch 更新次数 | 更多 | 更少 |
| loss 曲线 | 局部抖动明显 | 更平滑 |
| 风险 | 吞吐较低 | OOM，且需重调学习率 |

“batch 越大越好”是误解。大 batch 的吞吐和梯度稳定性可能更好，但每个 epoch 的更新次数减少，而且不能保证泛化更好。

### 3.3 LLM 还要看 token 数

文本长度可变时，“8 条样本”不等于相同计算量。8 条各 128 token 的样本，与 8 条各 4,096 token 的样本，注意力计算、激活值和显存差异极大。

因此大模型训练常同时观察：

- per_device_train_batch_size：单张 GPU 的样本数；
- max_length 或 seq_len：每条样本的最大 token 数；
- tokens_per_batch：每批实际 token 总数；
- effective_batch_size：跨卡、跨累积的总样本或总 token。

长度波动大时，按长度分桶、动态 padding、样本打包通常比盲目加 batch 更有价值。

### 3.4 选择起点的步骤

1. 固定模型、序列长度、优化器和数据处理。
2. 从稳定的小值开始，例如图像任务 32，LLM 微调每卡 1、2、4。
3. 逐步增加，记录峰值显存、samples/s 或 tokens/s、训练损失和验证指标。
4. 接近 OOM 前保留余量，给验证、保存 checkpoint 和偶发长样本留空间。
5. 再根据有效批大小重新检查学习率与训练更新数。

    from torch.utils.data import DataLoader, TensorDataset
    import torch

    dataset = TensorDataset(
        torch.randn(1_000, 20),
        torch.randint(0, 2, (1_000,)),
    )
    loader = DataLoader(dataset, batch_size=32, shuffle=True)

    for batch_features, batch_targets in loader:
        print(batch_features.shape)  # torch.Size([32, 20])
        print(batch_targets.shape)   # torch.Size([32])
        break

最后一个批次可能小于 batch_size。若需要固定形状可使用 drop_last=True，但会丢弃每个 epoch 最后的少量样本。

## 4. 学习率：每次参数更新走多远

最朴素的梯度下降公式是：

    θ_new = θ_old - η × ∇L(θ)

θ 是参数，L 是损失，∇L 是梯度，η 是学习率。梯度决定方向，学习率决定步长。

可以把它想成下山：

- 学习率过大：每次跨得太远，可能越过谷底，在两侧反复跳，甚至数值发散。
- 学习率合适：能够快速下降，并在低处逐渐稳定。
- 学习率过小：每次只移动一点，虽可能稳定，却很久才有改善。

| 现象 | 可能原因 | 首个排查动作 |
| --- | --- | --- |
| loss 很快为 NaN、inf 或爆炸 | 学习率太大，或有数值错误 | 学习率降 2 到 10 倍，检查数据与 AMP |
| loss 长期大幅跳动 | 学习率偏大，或 batch 很小 | 降低学习率，检查有效 batch |
| loss 平稳但几乎不变 | 学习率偏小，或梯度/数据异常 | 尝试适度提高，确认梯度非零 |
| 训练 loss 降、验证变差 | 通常不是单纯学习率问题 | 检查过拟合和数据划分 |

这些只是诊断假设。loss 不降也可能是标签错位、模型处于 eval()、优化器没有拿到参数，或忘记执行 backward()。

### 4.1 AdamW 仍要调学习率

    optimizer = torch.optim.AdamW(
        model.parameters(),
        lr=2e-5,
        weight_decay=0.01,
    )

AdamW 会维护自适应统计量，但 lr 仍是最敏感的超参数之一。预训练模型全量微调常见起点可能在 1e-5 到 5e-5；从零训练的小网络可能在 1e-4、1e-3 或更高。范围不能脱离模型、优化器、数据与训练目标照搬。

### 4.2 batch 改变时，为什么 lr 常要重调

有效 batch 从 32 增到 64 后，一次更新使用了更多数据，每个 epoch 的更新却变少。工程上有时用线性缩放规则作为起点：

    new_lr = old_lr × (new_effective_batch / old_effective_batch)

例如 32 到 64，1e-4 可尝试 2e-4。但它不是定律，尤其在小数据集、微调或极大 batch 下必须用实验验证。保守做法是先保持学习率，再在小范围搜索。

### 4.3 预热与调度器

Transformer 训练常用 warmup：从很小 lr 升到峰值，再衰减。训练开始时优化器统计量未稳定，直接使用目标学习率可能导致初期不稳。

    from torch.optim.lr_scheduler import LambdaLR
    import math

    total_updates = 10_000
    warmup_updates = 500

    def lr_ratio(step: int) -> float:
        if step < warmup_updates:
            return (step + 1) / warmup_updates
        progress = (step - warmup_updates) / (
            total_updates - warmup_updates
        )
        return 0.5 * (1 + math.cos(math.pi * progress))

    scheduler = LambdaLR(optimizer, lr_lambda=lr_ratio)

有梯度累积时，只在真实参数更新后调用 scheduler.step()。

## 5. 梯度裁剪：给异常更新加安全阀

反向传播经过许多层的链式法则。长序列、异常样本、过大学习率或不稳定配置下，梯度范数可能极大。即使学习率没变，学习率乘极大梯度也会产生破坏性更新，随后 loss 可能成为 inf 或 NaN。

梯度裁剪是在更新前限制极端梯度。它不是让模型更聪明，也不能修复数据错误；它的价值是防止一次坏更新摧毁训练。

### 5.1 两种常见方式

按值裁剪：逐元素限制范围。

    torch.nn.utils.clip_grad_value_(model.parameters(), clip_value=1.0)

按范数裁剪：若所有梯度的总范数超过阈值，按同一比例缩小所有梯度。大模型训练更常见。

    grad_norm = torch.nn.utils.clip_grad_norm_(
        model.parameters(),
        max_norm=1.0,
    )

例如原始范数 10、阈值 1，所有梯度约缩小为原来的十分之一，方向不变；原始范数 0.3 时不修改。

### 5.2 正确顺序与观察方法

    optimizer.zero_grad()
    loss = criterion(model(inputs), targets)
    loss.backward()
    grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    optimizer.step()

裁剪必须在 backward() 之后、optimizer.step() 之前。每隔若干更新记录裁剪前范数：

    if update_step % 50 == 0:
        print(f"grad_norm_before_clip={grad_norm.item():.3f}")

- 很少超过阈值：裁剪只是保险。
- 几乎每次远超阈值：继续检查学习率、异常数据、loss 标度和序列长度。
- 阈值太低：每一步都被压缩，模型会学得很慢。

max_norm=1.0 是常见起点，不是固定答案。

## 6. 梯度累积：显存不够时模拟大 batch

假设希望有效 batch=32，但显卡一次只能放 8 条样本。可以连续做 4 个小批次的前向和反向计算，把梯度累加在参数的 .grad 中，第四次再更新：

    微批次 1：反向计算，暂不更新
    微批次 2：继续累加梯度
    微批次 3：继续累加梯度
    微批次 4：裁剪并更新一次参数

    effective_batch = micro_batch × accumulation_steps × num_gpus

### 6.1 最容易漏掉的关键：loss 要除以累积步数

损失函数通常返回批次平均损失。四个微批次都直接 backward() 会让累积梯度变成四倍。要近似 32 样本大 batch 的平均梯度：

    loss = criterion(outputs, targets)
    loss = loss / accumulation_steps
    loss.backward()

忘记这一步，相当于把更新幅度放大 accumulation_steps 倍，行为近似于无意中把学习率放大。

### 6.2 可复用的 FP32 训练片段

    accumulation_steps = 4
    max_grad_norm = 1.0

    model.train()
    optimizer.zero_grad(set_to_none=True)

    for micro_step, (inputs, targets) in enumerate(train_loader, start=1):
        inputs = inputs.to(device)
        targets = targets.to(device)

        outputs = model(inputs)
        raw_loss = criterion(outputs, targets)
        (raw_loss / accumulation_steps).backward()

        is_update_step = (
            micro_step % accumulation_steps == 0
            or micro_step == len(train_loader)
        )
        if is_update_step:
            grad_norm = torch.nn.utils.clip_grad_norm_(
                model.parameters(),
                max_norm=max_grad_norm,
            )
            optimizer.step()
            optimizer.zero_grad(set_to_none=True)

最末组不足 accumulation_steps 时，上述代码仍会更新。若追求严格数学等价，应以末组实际微批次数调整缩放；入门阶段先掌握基本模式即可。

### 6.3 它并非完全等价大 batch

- Dropout、随机增强会令微批次随机状态不同。
- BatchNorm 依赖单个微批次统计量，微批次很小时行为会不同。
- 一个参数更新要跑更多前向/反向，墙钟时间未必更快。
- 分布式训练与动态 loss scale 会带来额外细节。

Transformer 多用 LayerNorm，因此梯度累积通常实用；依赖 BatchNorm 的模型要额外小心。

检查清单：

- 不能每个微批次都 zero_grad()。
- 每个微批次 loss 要除以 accumulation_steps。
- 只在更新点调用 optimizer.step()、scheduler.step() 和梯度裁剪。
- 日志最好记录原始 raw_loss，而不是已除后的 loss。
- 调度器总步数按更新次数，不按微批次数。

## 7. 混合精度训练：更省显存，也可能更快

浮点数位数少时，显存和带宽消耗更低，GPU 矩阵计算可能更快；代价是可表示精度或数值范围降低。

| 格式 | 优点 | 主要风险 |
| --- | --- | --- |
| FP32 | 数值稳定、范围较大 | 显存和计算成本高 |
| FP16 | 快、省显存 | 动态范围小，易上溢或下溢 |
| BF16 | 范围接近 FP32，通常稳定 | 尾数精度较低，需硬件支持 |

混合精度不是把所有计算强制改为半精度，而是让适合低精度的矩阵计算使用 FP16/BF16，让敏感计算保留安全精度。

### 7.1 用 autocast，而不是到处手工 half()

    with torch.autocast(device_type="cuda", dtype=torch.float16):
        outputs = model(inputs)
        loss = criterion(outputs, targets)

autocast 会按算子选择精度。手工 model.half() 可能使归一化、损失等敏感部分进入不合适精度，排错更困难。

### 7.2 FP16 为什么常配 GradScaler

FP16 对很小数字的表示能力有限，反向传播中的小梯度可能下溢为 0。GradScaler 先放大 loss，使梯度落在可表示范围，再在更新前恢复真实尺度：

    scaler = torch.amp.GradScaler("cuda")

    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = criterion(model(inputs), targets)

    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()

发生溢出时，scaler 可以跳过不安全更新并调整缩放比例。它不能修复坏数据或过大学习率。BF16 的指数范围接近 FP32，通常不需要 GradScaler。

### 7.3 AMP + 累积 + 裁剪的正确顺序

FP16 使用 GradScaler 时，裁剪前必须先 unscale；否则裁剪的是被放大的梯度，阈值没有意义。

    accumulation_steps = 4
    scaler = torch.amp.GradScaler("cuda")
    optimizer.zero_grad(set_to_none=True)

    for micro_step, (inputs, targets) in enumerate(train_loader, start=1):
        inputs = inputs.to(device, non_blocking=True)
        targets = targets.to(device, non_blocking=True)

        with torch.autocast(device_type="cuda", dtype=torch.float16):
            loss = criterion(model(inputs), targets)
            loss = loss / accumulation_steps

        scaler.scale(loss).backward()

        is_update_step = (
            micro_step % accumulation_steps == 0
            or micro_step == len(train_loader)
        )
        if is_update_step:
            scaler.unscale_(optimizer)
            grad_norm = torch.nn.utils.clip_grad_norm_(
                model.parameters(),
                max_norm=1.0,
            )
            scaler.step(optimizer)
            scaler.update()
            optimizer.zero_grad(set_to_none=True)

记忆顺序：

    autocast 前向与损失 -> scale 后向 -> 更新点 unscale -> clip -> step -> update -> 清梯度

建议先用 FP32 证明训练循环和数据正确，再单独开启 AMP，比对显存、吞吐、训练曲线和验证指标。若 AMP 才出现 NaN，先回到 FP32 定位。

## 8. 完整的小型实验

下面用随机二分类数据验证训练循环。它不解决真实业务，但能检查 loss、更新次数、梯度累积、裁剪与 AMP 的组合是否正常。

    import torch
    from torch import nn
    from torch.utils.data import DataLoader, TensorDataset

    torch.manual_seed(42)
    device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

    num_samples, num_features = 2_000, 20
    features = torch.randn(num_samples, num_features)
    true_weights = torch.randn(num_features, 1)
    logits = features @ true_weights + 0.2 * torch.randn(num_samples, 1)
    targets = (logits.squeeze(1) > 0).long()

    loader = DataLoader(
        TensorDataset(features, targets),
        batch_size=32,
        shuffle=True,
        pin_memory=(device.type == "cuda"),
    )

    model = nn.Sequential(
        nn.Linear(num_features, 64),
        nn.ReLU(),
        nn.Linear(64, 2),
    ).to(device)
    criterion = nn.CrossEntropyLoss()
    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)

    accumulation_steps = 2
    use_amp = device.type == "cuda"
    scaler = torch.amp.GradScaler("cuda", enabled=use_amp)

    for epoch in range(5):
        model.train()
        optimizer.zero_grad(set_to_none=True)
        running_loss = 0.0
        update_count = 0

        for micro_step, (x, y) in enumerate(loader, start=1):
            x, y = x.to(device), y.to(device)

            with torch.autocast(
                device_type=device.type,
                dtype=torch.float16,
                enabled=use_amp,
            ):
                raw_loss = criterion(model(x), y)
                loss = raw_loss / accumulation_steps

            scaler.scale(loss).backward()
            running_loss += raw_loss.item()

            if (
                micro_step % accumulation_steps == 0
                or micro_step == len(loader)
            ):
                scaler.unscale_(optimizer)
                grad_norm = torch.nn.utils.clip_grad_norm_(
                    model.parameters(),
                    max_norm=1.0,
                )
                scaler.step(optimizer)
                scaler.update()
                optimizer.zero_grad(set_to_none=True)
                update_count += 1

        print(
            f"epoch={epoch + 1}, "
            f"loss={running_loss / len(loader):.4f}, "
            f"updates={update_count}, "
            f"grad_norm={grad_norm.item():.3f}"
        )

观察点：

1. loss 的整体趋势应下降，局部波动正常。
2. 微批次为 32，有效 batch 是 32 × 2 = 64。
3. 使用 GPU 时，AMP 往往降低显存；是否加速取决于硬件和模型。
4. grad_norm 偶尔超过 1 正常；长期极端大才需排查。

## 9. 故障定位：按最小闭环排查

### 9.1 CUDA Out of Memory

优先顺序：

1. 降低每卡 batch size。
2. 降低最大序列长度，使用动态 padding，检查超长异常样本。
3. 启用 AMP。
4. 使用梯度累积恢复目标有效 batch。
5. 检查是否把未 detach() 的 Tensor 持续存进列表，导致计算图不释放。
6. 最后再考虑 checkpointing、LoRA/QLoRA、分布式并行。

反复调用 torch.cuda.empty_cache() 不能解决模型激活值真实占用过多的问题。

### 9.2 loss 变为 NaN 或 inf

按“输入 -> 数值 -> 超参数”排查：

1. 用 torch.isfinite() 检查输入、标签、输出与 loss。
2. 关闭 AMP，确认 FP32 基线是否正常。
3. 降低学习率。
4. 记录梯度范数并启用裁剪。
5. 检查标签范围是否匹配 loss，例如 CrossEntropyLoss 的标签应为 [0, num_classes - 1] 的整数。
6. 检查除零、log(0)、空序列和异常长度。

    def assert_finite(name: str, tensor: torch.Tensor) -> None:
        if not torch.isfinite(tensor).all():
            raise RuntimeError(f"{name} 包含 NaN 或 inf")

定位期要尽早失败，而不是让异常静默传播数十个 step。

### 9.3 loss 不下降

先做小数据过拟合测试：取 16 到 64 个样本，关闭复杂增强，固定随机种子，训练到几乎记住它们。若训练 loss 仍不能明显下降，优先查训练循环、标签、维度、优化器和模型，而不是泛化能力。

### 9.4 梯度累积后效果变差

检查四件事：

- 是否忘记 loss / accumulation_steps；
- 是否误在每个微批次 zero_grad()；
- 是否只在更新点执行 optimizer.step()；
- 调度器是否错误地按微批次推进。

### 9.5 AMP 后才出问题

先关闭 AMP 确认 FP32；支持时尝试 BF16；确认 FP16 使用 GradScaler，且裁剪前 scaler.unscale_(optimizer)；再降低学习率并检查自定义算子和异常样本。

## 10. 用实验而不是感觉调参

不要一次改五个旋钮。实验记录至少包括：配置、随机种子、代码版本、峰值显存、吞吐、训练损失与验证指标。

1. **batch 实验**：固定学习率和总更新数，尝试 [8, 16, 32, 64]，比较显存、吞吐、相同更新数后的指标。
2. **学习率实验**：固定 batch，尝试 [1e-5, 3e-5, 1e-4, 3e-4]，先短跑淘汰发散值，再完整训练。
3. **累积等效实验**：比较 batch=32、累积=1 与 batch=8、累积=4；二者有效 batch 都为 32，趋势应接近但不必逐位相同。
4. **AMP 实验**：在同一随机种子、batch、lr 下比 FP32 与 AMP，既看显存和 tokens/s，也看是否 NaN 与最终验证指标。

## 11. 推荐学习顺序

1. 用 FP32 写最小训练循环，在 32 个样本上过拟合。
2. 改 batch size，理解显存、吞吐、更新次数和曲线抖动。
3. 用固定 batch 搜索 3 到 5 个学习率。
4. 打印梯度范数，加入 clip_grad_norm_。
5. 降低微批次，用梯度累积恢复有效 batch。
6. 最后开启 AMP，并分别验证 FP16 + GradScaler 与 BF16。
7. 每一步保存配置和指标，不凭“看起来更好”判断。

完成后应能回答：

- 为什么有效 batch 不只是 DataLoader(batch_size=...) 中的数？
- 为什么累积时 loss 必须除以累积步数？
- 学习率过大与梯度爆炸有什么联系和区别？
- 为什么 FP16 裁剪前需要 unscale_？
- 遇到 OOM、NaN、loss 不下降时，分别先检查什么？

## 12. 总结

这五个机制共同管理三种资源：

- **统计资源**：每次更新用了多少数据，梯度噪声有多大；
- **数值资源**：前向、反向和更新能否稳定表示；
- **硬件资源**：显存容量、计算吞吐和多卡并行能力。

稳健做法是先用小规模 FP32 基线证明训练循环正确，再逐一启用更大的有效批大小、梯度裁剪、梯度累积和 AMP，并让每次改动都有可比较的日志与验证指标。这样遇到问题时，你是在做有证据的工程排查，而不是盲目试参数。
